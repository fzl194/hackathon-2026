# **云运维场景智能问数查询优化**

# **二、背景信息**

## **2.1** **问题背景**

面向全栈云的运维智能体，正在朝 L4 自动故障快恢方向发展。在 AI 自动故障快恢过程中，涉及大量 AI 的自主可观测数据查询，往往占端到端时长 70% 以上。数据查询效率直接决定华为云运维智能体故障快恢效率。基于数据本体 + ReAct 方式的智能查数，虽然能保证准确率，但每道题都要经历"推理—试查—纠错"的多轮循环，执行时长通常可长达 45 秒到 1 分钟，且同类问题反复从零推理——这对要求故障快恢 10 分钟闭环的业务要求造成巨大挑战。

破局的关键在于 **Agent** **执行经验的蒸馏与复用**：大模型每次成功的 ReAct 查询，都是一次宝贵的执行经验——问题如何理解、条件如何拆解、查询如何构造。如果让这些经验随用随弃，智能体永远停留在"每次从零推理"的初级阶段；如果能将成功的执行经验沉淀、蒸馏为可复用的查询模板，运行时通过快速模式匹配直接复用，常用查询的执行速度就能提升到 5 秒以内，AI 自主故障快恢的端到端时间有望从 15 分钟降低到 8 分钟以内。经验的自动沉淀与蒸馏能力，正是运维智能体从"会解题"进化到"越用越快、越用越准"的核心分水岭。

在华为云场景中，资源管理数据库涵盖约700种资源类型、约5万个字段和2000+条资源间关系；实际环境中资源实例总量超过2,500万条，资源间关系记录约6,000万条，涵盖端口—子网、云硬盘—虚拟机挂载、负载均衡—后端服务器、安全组—实例绑定等拓扑关联。监控数据库定义了2000左右监控指标索引，文档总量将近2500万。数据横跨计算、存储、网络、容器、中间件、数据库、应用等全域资源。呈现出规模大、维度多、关联复杂的特点。因此，选手的查询模板与检索算法必须能在如此真实量级的环境中快速、准确地命中并执行。为此，本题将提供基础实现，方便选手在最小实现的基础上集中优化精度和性能，从而降低参赛门槛。

## **2.2** **问题难点**

本题要求设计一种查询模板提炼与运行时高性能匹配的算法和系统，既能让大模型在线精确分析问题、快速提炼模板，又能在运行时高效、准确地命中查询模板——保证 80% 常用查询命中模板、端到端耗时 3 秒以内，仅长尾查询送大模型进行 ReAct 查询。具体难点包括：

**经验的自动沉淀与蒸馏**：大模型需在 ReAct 查询过程中自动识别高频查询意图，将成功的执行轨迹蒸馏为参数化查询模板——从具体执行中剥离实体值、抽象出查询骨架与可填充参数；蒸馏过程不依赖人工审定，且必须保证模板语义的正确性与可执行性，蒸馏出的错误经验会以模板形式被反复放大。

**通用性与模板数量的矛盾：**以 150 条模板覆盖 200 种真实查询意图，且模板越少加分越多——单条模板必须通过参数化抽象覆盖一族同构问题，换实体、换区域、换措辞均应稳定命中，而非一题一模板。

**原子性与组合求解：**模板职责单一、接口正交；复合问题需自动拆解为 2~4 条原子模板并行或级联执行并汇聚结果，不允许为组合场景单独建模板。

**高性能运行时匹配：**运行时模板检索须在毫秒级完成（单题检索 ≤ 200ms），且模板库规模增大时，匹配延迟与误匹配率不能显著劣化。

**高准确率与可拒绝能力：**命中错误模板比不命中更危险。匹配置信度不足时必须能安全弃权（拒答不扣分，误答扣分），保证 precision 优先；同时常用查询命中率不低于 80%，兼顾 recall。

**判别条件的敏感性：**检索需对改变语义的判别性条件（如可用区、租户等限定词）保持敏感，同时对无关修饰（区域前缀、不可预知的实体名格式）保持条件不变性。

**准确检索与误匹配控制：**一个问题往往同时关联多条模板，需把相关模板全部准确检索出来；而模板间措辞相近、问题表述多样，极易误匹配——误选的模板会导致后续查询无关数据，既浪费执行时间又污染最终结果，检索的准确性与完整性（找得准、找得全、不误召）本身就是核心难点。

# **四、期望达到的指标和效果**

## **4.1** **功能目标**

- 实现端到端的自然语言查询：输入运维问题文本，输出结构化查询结果集；
- **查询经验的自动沉淀与高性能复用（方向引导与拔高项）：**大模型在线精确分析问题、自动提炼参数化模板，运行时高性能匹配命中，未覆盖的长尾查询可安全拒答，形成“在线学习—模板沉淀—毫秒复用”的自动闭环；
- 工程接口解耦：执行器与评分器接口固定，模板库、检索器、智能体可独立替换优化。
- 鼓励引入小模型对流程进行加速/准确率提升，但是确保不超过内存限制。

## **4.2** **性能目标**

| **指标** | **要求** |
| --- | --- |
| 模板命中率 | 80% 以上常用查询命中模板，并在此基础上越高越好 |
| 命中题端到端耗时 | 3 秒以内（挑战目标 5 秒 SLA 内），并在此基础上越低越好 |
| 整体时延 | 95% 的查询问题在 20 秒内完成从问题输入到结果返回 |
| 模板效率 | 目标 150 条；同等准确率下，模板条数少者排名靠前 |

# **七、评选标准**

## **7.1** **单题评分**

具体评分细节以 SDK 包中的评估器为准，本节为规则摘要。

每题满分 5 分，每题测试 2 次取平均。按以下顺序逐项检查，命中即返回：

| **检查项** | **情况** | **得分** |
| --- | --- | --- |
| 弃权 | 系统未产出结果，或未命中模板 | 0 |
| 执行错误 | 查询请求执行失败等运行时异常 | -1 |
| API 条件检查（硬门槛） | 标准答案带查询条件而系统未带（疑似全量拉取后本地过滤）；标准无条件则不要求 | 0 |
| 答案完全正确 | 行数匹配且所有行值匹配（含数值容差） | +5 |
| 部分正确 | 匹配率 ≥ 50%，按 round(5 × ratio, 1) 计分 | 按比例 |
| 答案错误 | 匹配率 < 50% | -1 |
| 超时扣分（取最高档，不叠加） | 响应时间 > 4s 扣 1 分；> 6s 扣 3 分 | -1 / -3 |

 

## **7.2** **模板数量评分**

目标模板数 150 条：每少一条加 1 分（+(150-N)），每多一条扣 1 分（-(N-150)）。

## **7.3** **最终得分**

用例权重：黑盒用例 100 题占 70%，白盒用例 200 题占 30%。不归一化，直接用原始分：

用例总分 = 黑盒原始分 × 70% + 白盒原始分 × 30%

最终得分 = 用例总分 + 模板数量得分

| --- | --- | --- | --- |
| 黑盒用例 | 44.9 / 500 | 70% | 31.43 |
| 白盒用例 | 554.1 / 1000 | 30% | 166.23 |
| 用例小计 | — | — | 197.66 |
| 模板调整 | 200 vs 150 | — | -50 |

- 违反检索器技术限制（使用向量/神经网络/外部模型等），取消成绩；
- 总分相同时，模板条数少者排名靠前（奖励通用性设计）；
- 评测脚本输出诊断指标（检索命中率、单题耗时、token 消耗）供选手定位瓶颈，诊断指标不计入总分。

## **7.4** **白盒评价与注意事项**

本赛题采用白盒评价：选手提交的工程文件夹与评测全链路日志（检索候选 → 模板选择 → 填充后的查询请求 → 执行结果 → 比对明细）均向评委公开，评审时结合代码与日志综合判断。请注意：

- **拒答优于误答：**未命中模板时拒答得 0 分，误命中导致答错扣 1 分——置信度门禁本身就是设计考点；
- **隐藏实体值替换测试：**评测器会将模板与代码中的条件值替换为隐藏实体值重新执行，凡依赖记忆公开用例实体值的设计都会在此环节暴露；
- **检索器合规审查：**检索器代码将在禁网络、禁外部模型文件的隔离环境中运行，并辅以人工审查，任何形式的向量/神经网络方案一经发现取消成绩；
- **模板容量限制的设计意图：**单条模板 ≤4KB、嵌套 ≤4 层是让模板回归“查询模板”本职，提示词工程请放在智能体（环节②③）的实现中，那是合法的优化空间；
- **最小实现即起点：**赛题提供可运行的最小实现与 SDK 包，允许任意修改乃至重写——但评测器接口与执行器接口约定（数据库查询 API）不可变更；
- **争议处理：**选手可申请查阅自己任意一题的完整评测日志，评分异议以日志记录为准。
