# 30 Web Agent 的并行执行与容错调度：技术解读与研究结论

> 研究日期：2026-10-11。面向会编程、不了解行业的读者，按 ELI5 技能先类比再解释。官方要求以[原文](原文.md)及[官网](https://www.chaspark.com/#/races/competitions/1326718923356090368)为准；下面技术路线与工时是研究判断；官方事实、外部资料和待做实验分别标注，未开展实际解题实验。

## 先弄懂它在做什么

像安排几位办事员同时跑不同窗口，但转账或填表前必须先拿到前一步材料；提交后要查是否真的办成，失败重跑还不能重复创建记录。窗口又有限流，不能用疯狂点击换速度。

领域是 **鸿蒙应用／真实网页Agent／并行容错**。本题是一个真正运行在鸿蒙平台上的网页办事员：理解任务、跨站执行、确认结果、失败恢复和限流。像安排多人办手续，读资料能并行，但提交订单必须避免重复。

## 官方任务、提交与评分

交鸿蒙应用工程，接受自然语言，在竞赛电商/论坛/代码托管/CMS网站完成跨站批任务；任务拆解、网页理解、执行、确认与恢复均自建。需完整日志、3—5页报告与现场复测。模型仅端侧或同算力，总参数≤32B；外部模型禁用，登录/二次验证可人工辅助。

**计分与硬门槛：** 验收通过率≥60%进入排名；成功/鲁棒45%、时间20%、操控质量15%、成本10%、报告10%。单任务二值，无部分分；失败不影响其他任务；禁止绕网页改后台和写死答案。

先把“能提交合法结果”和“分数有优势”分开验证。优化动作是否有用，应以官方计分对象与完整链路验证，不以行业常用指标或演示效果代替。若未发布具体规则，不能假设所有细节与公开论文一致。

## 已有背景与可参考资源

**本轮核验：** 本轮检索鸿蒙Web交互官方资料，并打开OpenHarmony官方docs的Web FAQ，确认WebviewController.runJavaScript能异步执行页面脚本并取回结果，调用需页面就绪。旧HarmonyOS Java WebView教程与ArkTS平台不是同一套API，不能混用；WebArena背景也不能代替真实鸿蒙工程。

- [OpenHarmony官方Web FAQ](https://github.com/openharmony/docs/blob/master/en/application-dev/faqs/faqs-arkui-web.md)：**支撑点：** runJavaScript异步执行与回调、页面加载时机、JSBridge用于应用读写DOM。 **借鉴边界：** OpenHarmony文档的API版本与比赛HarmonyOS SDK需对齐，网页动作接口不自动提供任务规划或容错。

- [官方鸿蒙Web Agent交付与验收](https://www.chaspark.com/#/races/competitions/1326718923356090368)：**支撑点：** 真实鸿蒙应用、≤32B端侧模型、60%门槛和二值后端校验，决定可靠性优先。 **借鉴边界：** 任务、站点和设备现场才给；本地站点通过不代表官方成功率。

## 训练、数据和提前准备的边界

**训练判断：** 轻量可选：可用现有端侧模型推理，不要求训练；LLM推理算力仍必要。

**数据依赖：** 高：未知网站DOM、任务与异常模式现场适配；已有通用Agent帮助但无法保证60%。

拿不到官方数据时，可以准备解析、验证、算法骨架、可复现构建和合成边界样例；公开资料/自造数据用于练习机制及排错。用它们得到的提升不能直接当成隐藏集提升。现场最先核对字段、单位、规模和可见信息，再跑已准备的基础版；不能把未来记录、隐藏标签或场外服务作为必需依赖。

## 可执行方案与竞争力

**最小可交付方案：** 鸿蒙应用支持Web执行脚本与DOM读取，规则工具完成常见操作，小模型只拆解任务；按任务DAG两路并发，提交后定向验收。

**进阶路线：** 状态日志+可恢复检查点，重复提交前查询结果；按网站调整并发/退避，对只读任务批量化，错误定位后局部重试。

**核心竞争力：** 结构化任务计划、并发只放独立步骤、写操作幂等检查、失败确认后恢复、网站级速率预算。建议先比较基础版与一次关键改动，用消融说明改进来自哪里；不要同时改多项后只看总分。

**降级与止损：** 降到低并发可靠DOM工具，缩小模型调用和搜索深度；每任务超时独立退出保其他任务，不把人工介入扩展成代做任务。交付必须保留一个经完整验证的版本，新优化只有验证通过后才成为最终提交。

## 技术栈、硬件与工作量

技术栈建议：ArkTS/DevEco、HarmonyOS Web组件、端侧LLM、小任务DAG、检查点、令牌桶。

硬件：官方鸿蒙应用、≤32B模型端侧或同算力；实际设备与加速能力未给；建议先选能流畅运行的小量化模型，GPU非训练必需但推理速度需实测。

技术难度 **5/5**（越高越难）；提前准备约 **130—220人时**，现场适配优化约 **34—55人时**。假设三人只主攻这一题，前期已完成最小闭环；范围含基本测试与材料，设备/依赖故障会额外占用。24小时虽理论72人时，考虑休息、沟通与串行依赖，有效估45—55人时；不能把三人并行当成所有步骤都能三倍加速。

分工可按“主力策略/模型、队友状态与数据校验、第三人接口回归与材料”组织，先给第三人明确可独立验证的任务。硬件中标明官方的内容是要求，建议项是准备配置，不能互相替代。

## 14天准备与现场24小时

**提前：** 第1—4天必须完成鸿蒙应用+端侧模型+Web桥接；5—9天自建跨站任务；10—12天注入超时/登录/限流；13—14天未知页面演练≥60%。

**现场：** 0—4小时站点适配与登录；4—10小时保住任务验收；10—16小时并发和恢复；若10小时通过率<60%，立即停性能优化只救正确性。最终提交前留出一次全新目录/离线启动复现，确认日志、文件格式、必需材料和随机种子；不是只在开发机器上跑成功。

## 调研后的结论与动手入口

**结论：先证明真实鸿蒙应用中的端侧模型、Web桥接和可靠串行任务，再加并行。** Agent经验能迁移，但不等于鸿蒙平台已经跑通。≤32B是参数上限，可从小量化模型加结构化DOM工具开始，不必训练大模型。

**动手入口：** 将任务拆成有前置条件/后置条件的DAG，DOM动作取回明确结果，写操作记录意图并提交后查询确认。超时先判断是否已生效，再重试，避免重复周报。并行只放独立读取与无写冲突节点，站点分别令牌桶限流，登录/二次验证暂停后恢复检查点。

**第一项小实验（待做）：** 两个自建站点的跨站周报任务，注入延迟、提交成功响应丢失、登录过期和限流。比较串行、盲目并发、带恢复的2路并发，记录二值成功率、重复写入、通过任务总耗时、访问次数和模型调用。60%是继续条件，还必须在真实鸿蒙端侧运行；本地网页脚本通过不能冒充应用交付。

**后续与时间边界：** 14天资产是目标SDK工程、Web脚本回调、小模型推理、状态机与真实审计日志；24小时主要适配官方DOM、任务词汇和限流，未达60%时只救正确性。OpenHarmony runJavaScript支持页面就绪后的异步读写，API版本需对齐HarmonyOS，旧Java教程不能混用。设备推理速度、任务时限和同等算力部署口径未知；允许脚本不等于允许绕网页改后台，外部模型明确禁用。

**还需核实：** 设备/SDK版本、端侧加速、同等算力模型的部署口径及实际网站DOM未定，推理延迟可能吞掉并行收益。允许页面脚本不意味着能绕网页直改数据库；外部模型、预写答案和日志伪造明确禁用。模型训练可选，实际推理能力仍需设备验证，ACM与Agent能力不能替代鸿蒙工程验证。
