# 第14题：从算法选手到能修改数据库向量索引

面向：熟悉编程和算法、没有数据库背景的参赛者。整理：2026-10-21。

这里先建立整题的直觉，再逐课深入。后续课程的实验尚未执行；学懂概念、代码能运行、满足题面、获得性能提升，是四种不同的进展。

## 1. 把整道题翻译成一个你熟悉的问题

给定N个d维向量，每次输入查询向量q，返回距离最近的K个向量的编号。数据太大，内存装不下；还会持续插入、删除和修改；查询可能附带标签要求；程序崩溃重启后仍须正确。

最后这个程序要成为PostgreSQL的一种索引，能够被SQL查询调用。

可以先把它想象成ACM问题的扩展：

```text
静态数组上Top-K
  → 用数据结构减少计算
  → 数据放不进内存，减少随机磁盘访问
  → 支持增删改和标签限制
  → 多个用户同时操作，提交/撤销和崩溃恢复都正确
  → 接入PostgreSQL并跑规定基准
```

前两步偏算法；中间偏系统；后两步涉及数据库。每一层都会影响下一层的设计。

## 2. 向量是什么，为什么业务需要找最近邻

假设一篇文章已经被某个模型转成一串数字：`[0.13, -0.27, ...]`。这是embedding，可以理解成机器生成的特征坐标。

业务希望“猫的文章”和“猫的查询”在这个坐标空间里更近。实际含义由生成向量的模型决定，并不是每一维都能解释为某个明确属性。

本题的检索基准主要给已经生成的向量。我们接手的是这些数字，负责快速搜索；不需要先训练一个文本或图像模型。图片数据来源也不意味着要做图像识别。

用二维先代替3072维：查询q=(0,0)，有A=(1,0)、B=(0,2)、C=(3,4)。按欧氏距离，依次是1、2、5，所以Top-2是A、B。3072维只是距离计算中有3072项，基本任务没有改变。

常见距离先理解用途，再记公式：

|距离|通俗理解|需要注意|
|---|---|---|
|L2|两点直线距离|排序时可比较平方距离，省去开方|
|L1|各坐标差的绝对值之和|与L2可能得到不同的近邻顺序|
|余弦|主要比较方向|常用距离为1−cos；零向量需明确处理|
|负内积|点积越大越好，所以取负后按升序|未归一化时不能随意当作L2|
|汉明|两个bit串有几位不同|可通过XOR和popcount计算|
|Jaccard|两个集合不相同的程度|bit形式可利用AND/OR与popcount；空集边界要遵循接口定义|

对归一化后的非零向量，L2平方等于2−2×内积，因此L2、负内积、余弦可以有一致排序。这个等价依赖归一化条件，不能推广到全部原始数据。

## 3. 数据库在这里究竟做什么

先把数据库表看成一个由数据库管理的记录集合：

|id|正文|标签|embedding|
|---|---|---|---|
|1|文章A|猫、宠物|一串数字|
|2|文章B|狗、宠物|一串数字|

SQL是向数据库表达需求的语言。下面这句表示“按向量距离从小到大，取前10条”：

```sql
SELECT id
FROM documents
ORDER BY embedding <-> '[0.1, 0.2, 0.3]'
LIMIT 10;
```

这是三维示意，不是完整建库脚本。`<->`是pgvector提供的L2运算符。上层用户表达“我要什么”，数据库决定“怎样取”。

数据库索引就是另外维护的加速结构。你熟悉的哈希表、平衡树都可以帮助理解索引：提前花时间和空间组织数据，换取查询更快。表是原始记录，索引帮助定位记录；新增、删除、修改时也要维护它。[PostgreSQL索引介绍](https://www.postgresql.org/docs/18/indexes-intro.html)

普通B-tree擅长按一个可排序的键查找、范围查找。高维近邻关系很难由一个一维排序完整保留，所以需要专门的向量索引。

PostgreSQL是数据库本体；pgvector是扩展，为它增加向量类型、距离运算和索引；pgvectorscale又提供另一种向量索引实现。算法名、软件库名和数据库扩展名不是同一层东西。

## 4. 从暴力解开始，才能理解ANN

最直接的方案：对N个向量逐个算距离，用大小K的堆维护答案。距离计算约O(Nd)，维护堆约O(N log K)，内存之外还要读取原始数据。

这是精确最近邻搜索。在小数据上非常有价值：它能给其他算法判答案。

ANN是近似最近邻搜索：通过少看一些候选，换取更快的查询，允许漏掉部分真正最近的点。这里的“近似”主要指搜索结果允许遗漏；不一定意味着距离公式算错，也不一定意味着用了压缩。

设精确Top-10为G，算法返回Top-10为A，没有重复编号时：

```text
recall@10 = |A ∩ G| / 10
```

找对9个就是0.9。通常对许多查询再取平均。它衡量与向量空间精确答案的重合，不是人类认为文章有用的比例。距离并列等细节还要遵循评测器的具体口径。

QPS是每秒完成多少次查询。延迟是一次查询等待多久。多线程和并发可以提升QPS，因此QPS不能直接取倒数当作每次查询延迟。

搜索更多候选，通常召回更高、速度更慢。比赛看一条召回—速度曲线，并在指定区间计算前沿面积；不能用0.80召回时的速度去打败别人在0.99召回时的速度。权重和淘汰项见[赛题解读](赛题解读.md)。

## 5. 主流算法先分成两种导航方式，再看压缩

### 5.1 IVF：先分区，再搜索少数分区

想象把城市分成很多片区，每个片区有一个代表点。建索引时，通过聚类等方法形成片区，把向量分配进去。查询时，先找最接近q的几个代表点，再检查对应片区的向量。

检查的片区越多，越不容易漏答案，但查询越慢。分区边界附近的点是典型难点：真正的最近邻可能在另一个没检查的片区。

IVFFlat保存未做PQ压缩的向量；IVF-PQ把片区中的向量再编码压缩。IVF的聚类和PQ码本通常要从样本中学习，这属于索引构建中的训练，与训练大型神经网络不同，但也要花构建时间。[Faiss索引说明](https://github.com/facebookresearch/faiss/wiki/Faiss-indexes)

### 5.2 图搜索：从入口走向越来越像的点

每个向量是一个顶点，边连接一些有助于导航的向量。从一个入口出发，计算已知候选与q的距离，优先扩展最有希望的点，逐步接近答案。

你可以用“优先队列＋visited＋受限候选集”理解其骨架。它不像Dijkstra那样最小化路径长度：优先级主要是向量到q的距离，边是导航工具，通常没有精确最短路式的完备性保证。

HNSW在图上增加多层结构：高层点少，快速靠近目标区域；底层点多，再精细搜索。类比跳表有帮助，但不能把跳表的严格分析直接搬过来。[HNSW作者论文](https://arxiv.org/abs/1603.09320)

图也不是简单地“每点只连最近的M个点”。边需要提供不同方向和跨区域的导航能力，否则可能在局部绕圈或绕很远。如何构图、选边和控制候选数量，是后续课程的核心。

### 5.3 DiskANN：把图搜索按SSD的特点重新设计

SSD比内存访问慢，所以不能只把一个为内存设计的图写成文件就期待同样快。

经典DiskANN结合Vamana图、内存中的压缩表示、SSD上的详细节点数据，以及缓存和批量读请求。压缩表示帮助便宜地判断“谁更值得看”，读取少数节点后继续导航，并用更准确的信息形成结果。具体组件和数据布局以选定版本为准。[DiskANN原论文](https://papers.nips.cc/paper_files/paper/2019/hash/09853c7fb1d3f8ee67a61b6bf4a7f8e6-Abstract.html)

### 5.4 量化：把地图缩小，最后再核对

量化是用较少的比特近似表达向量。例如8维float32需要32字节；PQ可以把它切成4段，每段用一个字节记录最接近的码字编号，总计4字节，不计共享码本。压缩后距离有误差，因此常配合原向量重排序。

这只是解释编码原理的例子，不是本题推荐参数或实测压缩比。二值量化又是另一类压缩方式，不能把PQ、二值量化和float16混为一个算法。

重要限制：真正近邻如果根本没进入候选集合，最后再精确重排也救不回来。

|方法|减少什么|主要代价或风险|
|---|---|---|
|暴力扫描|不减少候选|计算量、读数据量大；但适合判答案|
|IVF|只查部分分区|漏查分区；聚类和选择分区数|
|HNSW|沿图只访问部分点|图内存、构建、维护；超内存访问性能|
|DiskANN类|减少搜索工作，并控制磁盘访问|构图、压缩误差、I/O布局与调度|
|PQ/二值等量化|每个向量的表示和计算成本|信息损失；可能需要读原向量重排|

量化可以和图、IVF组合；这些并非互斥的五种产品。

## 6. 为什么“放到磁盘上”会改变算法选择

在ACM中常把数组访问看成O(1)。这里必须继续问：访问的是内存，还是要等SSD？是连续读，还是随机读？读来的一页能用几个点？

用下面的成本拆分作直觉，不当作精确性能公式：

```text
一次查询成本 ≈ 距离计算 + 不能被并行/缓存掩盖的磁盘等待
             + 数据库处理和并发协调
```

算得少但每一步都随机读盘的算法，可能输给多算一些、读得更连续的算法。优化CPU代码前，要先测是否主要在等磁盘。

规模也要认真算：

- 10亿×128维×4字节，float32纯向量约512GB。
- BIGANN上游原始表示通常为uint8，相同条数的纯向量为128GB；导入float32后会膨胀，不能混报。
- 100万×3072维×4字节，约12.288GB，尚未加表、索引、日志和临时空间。
- 一个3072维float32向量自身12,288字节，超过PG常见8KiB页面。表能通过大字段机制存储，不等于特定索引能把完整节点塞进单页。

前两条的BIGANN数据类型以[上游数据集定义](https://github.com/harsha-simhadri/big-ann-benchmarks/blob/main/benchmark/datasets.py)及实际文件为准；数字是载荷算术，不是下载包或总索引大小。

## 7. 过滤和更新为什么会另成赛道

过滤：在所有文章里找最像的10篇，与“只在同时带猫和医学标签的文章里找最像的10篇”，答案不同。

先全局找10篇再过滤，可能一篇不剩。先筛出全部合格记录再精确搜索，遇到候选很少时可以很快，但候选很多时也可能很慢。边走图边过滤有潜力，然而如果禁止经过不合格节点，又可能切断通向答案的路。

因此要区分“可以经过的导航点”和“可以返回的答案点”。选择率、标签分布及双标签交集，会改变最优策略。AND是两个条件都满足，OR是至少一个满足，不能替换。

更新：插入点要能被搜到，删除点不能再作为当前答案；删掉一个导航桥梁后，其他点也不能突然变得难找。图的连通性、旧空间回收与增量维护都影响长期召回。

## 8. 数据库正确性：这层不能用召回来替代

ANN允许漏掉合法近邻；事务错误不能解释成“近似”。

|场景|最简单的要求|后续要学习的机制|
|---|---|---|
|插入后ROLLBACK|撤销后，该记录不能作为正常查询结果出现|事务、索引记录可见性|
|其他会话还没提交|不能让查询读到不该看的数据|MVCC：用版本和快照判断谁能看哪条记录|
|提交后进程崩溃|恢复后数据库和索引要一致|WAL：数据页持久化前先保证相关日志持久化|
|两个线程同时改邻接表|结构不能写坏，也不能发生不受控等待|锁、页修改协议、并发设计|
|旧版本不再被需要|能够安全回收空间|VACUUM及索引清理|

MVCC不是让所有查询永远看到同一个快照；快照范围取决于事务隔离级别。索引内部保留旧条目也不一定是bug，关键是返回的表记录满足当前可见性，且能安全维护与回收。[PG并发控制](https://www.postgresql.org/docs/18/mvcc-intro.html)、[WAL](https://www.postgresql.org/docs/18/wal-intro.html)

查询规划器则像执行前的策略选择器：先过滤再精确算，还是走ANN索引？索引必须向数据库提供可信的成本与调用能力。简单强制“每次都用我写的索引”不是完整的规划器集成。

## 9. 现有开源软件做到哪一步

pgvector已经有类型、距离、精确搜索、HNSW和IVFFlat，以及数据库集成，是学习和验证的重要参照。其HNSW的vector索引上限2000维，halfvec为4000维；它能把索引持久化到磁盘，不能表述成“完全不能存盘”。本题担心的是超内存时的性能和完整能力。[pgvector](https://github.com/pgvector/pgvector)

pgvectorscale已有StreamingDiskANN和量化、标签过滤，可以研究数据库中的磁盘图索引怎样落地。但其公开接口距离覆盖、smallint标签范围、OR语义等与题面有差距，不能直接安装后宣布完成。[pgvectorscale](https://github.com/timescale/pgvectorscale)

公开数据集上的成绩和可比条件单独整理在[公开基准现状](公开基准现状.md)。本项目当前没有任何自测QPS，也没有完成扩展。

## 10. 后续按这条路线逐步学习

不把“精通”当作读完术语表。每一课都需要能解释、能操作、能验证的产物。下面是课程计划，不表示已经完成实验。

|课次|重点|动手产物|过关标准|
|---|---|---|---|
|1，本篇|整题、SQL、Top-K、召回与磁盘直觉|手算一个小数据例子|说清ANN允许什么误差、事务不允许什么错误|
|2|PG最小入门：表、索引、事务、EXPLAIN|小型SQL实验与执行计划|解释同一句查询为何走不同路径；看懂回滚|
|3|暴力精确搜索与评测|独立真值、recall计算器、小数据回归|知道程序算错距离、搜漏答案、评测口径错误如何区分|
|4|IVF、HNSW逐步手推与代码|二维可视示例、候选队列追踪、参数曲线|能解释增加搜索预算为何通常改善召回|
|5|Vamana、PQ、SSD布局和缓存|读写路径图、CPU/I/O分析、受限内存实验|能说明一次搜索实际读了什么，瓶颈在哪里|
|6|PG索引扩展：页、回调、MVCC、WAL、VACUUM|基线源码导航和事务/恢复回归|解释提交、回滚、删除、恢复分别依靠哪层保证|
|7|高维、AND过滤和动态维护|四赛道小闭环及功能差距表|不靠降低语义要求通过演示|
|8|优化、消融、复现和报告|完整曲线、资源记录、可重复构建|性能收益有相同条件下的证据，交付物可复现|

进入开发时，先比较候选实现的硬要求覆盖，再决定修改哪一层。当前值得验证的方向是“成熟PG集成基础＋受限内存搜索设计”，并未决定采用哪个库，更未证明它能获奖。

AI可以辅助讲源码、写小实验、构造反例和分析日志。重要结论需要我们能说出原因，再用程序和基准验证；生成出来的实现不算已掌握，更不算已通过评测。
