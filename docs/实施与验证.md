# 实施与验证

当前仅有题面和技术研究，以下是待执行计划。目标固定为第14题，不再比较选题。

## 先形成可复现闭环

1. 确认正式PG版本、Linux/容器环境、CPU/RAM/SSD限制，锁定依赖与源码提交。
2. 验证候选扩展在PG18.4的干净构建、CREATE EXTENSION、建索引与查询。
3. 用小数据做精确Top-K参照，检查全部必需类型/距离、高维和过滤。
4. 验证事务、并发、删除、回滚和重启恢复，形成独立回归。
5. 接入四赛道的调用/数据/参数扫描与结果导出，再扩大到受限内存数据。
6. 以相同资源预算比较完整曲线、构建成本和动态检查点，逐项做优化及消融。

官方调度或适配未取得前，上游基准只能作为准备入口，不能称已通过正式评测。

## 必须维护的验证矩阵

|维度|验证内容|需要保留的证据|
|---|---|---|
|类型×距离|vector/halfvec/sparsevec各4种，bit两种|SQL、精确参照、ANN结果与误差/召回|
|高维|指定3072维数据建索引、查询|构建日志、资源、召回—QPS曲线|
|超内存|数据/索引明显超过实际内存预算|统一内存限制、峰值、读写/缺页、吞吐|
|事务|提交、回滚、更新、删除的可见性|不同隔离/会话的查询断言|
|恢复|干净重启与故障恢复后的一致性|恢复过程、数据/索引核对|
|并发|后台写入与查询同时进行|正确性、延迟、QPS、锁与失败日志|
|过滤|单/双标签AND、选择率变化|过滤后的精确Top-K及召回曲线|
|动态|逐runbook操作和查询检查点|检查点召回、耗时及内存|
|提交|干净Docker构建、配置扫描与离线复现|版本清单、构建命令、结果与报告|

每次实验记录源码提交、配置、随机种子、数据来源/版本、硬件、内存限制、构建与查询时间。缓存冷热状态必须可解释，不能用不同资源或不同缓存条件展示虚假收益。

## 基线差距清单

对pgvector、pgvectorscale或其他实现逐项标记“已验证/缺失/待核”，包括：全部类型距离、3072维、超内存、标签范围与AND、动态维护、事务/恢复、PG18.4、基准适配。当前没有任何一项被本项目实测确认。

若使用外置索引文件，需要明确WAL、提交/回滚、MVCC、崩溃恢复和并发的一致性设计。数据库表写成功后再写外部文件的双写流程，不能默认满足事务要求。

## 优化顺序

先解决淘汰项和可复现性，再做页布局/缓存、导航量化与重评分、过滤遍历、动态维护、构建吞吐及规划器成本。一次只引入可解释的改动，并记录完整recall—log QPS前沿，不只展示最佳单点。

正式数据到手后优先确认版本与资源、跑回归和小规模闭环，再排构建与参数扫描；最后留出冻结、干净构建、报告和提交复测的时间。超大数据构建由谁执行、能否预制索引或下载缓存，必须先确认。
