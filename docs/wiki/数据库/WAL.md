# WAL：先保证日志持久化，再允许相关数据页落盘

[返回 Wiki 首页](../README.md) · [第14题全貌](../第14题全貌.md)

**一句话：WAL 通过规定日志与数据页的持久化顺序，让数据库能在崩溃后恢复修改。**

全称是 Write-Ahead Logging，预写日志。这里的“先”主要指先于相关数据页持久化，不是说修改内存之前必须先同步写磁盘。

## 为什么需要这层机制

数据库会缓存数据页。你可以先把“页”理解成数据库读写文件时管理的一块数据，里面可能放表记录或索引内容。

为了速度，修改通常先发生在内存中的页上，随后才写回数据文件。如果每次提交都要把全部相关数据页立即写盘，随机写入和等待成本会很高。

WAL 换了一种办法：记录能够用于恢复修改的日志，保证日志先可靠保存，再允许相关数据页持久化。

## 一个简化流程

以正常持久化配置下的一次同步提交为例：

```text
1. 修改内存中的数据页，并产生相应 WAL 记录
2. 提交时，等待所需 WAL（包括提交记录）持久化
3. 向客户端确认提交成功
4. 尚未写回的数据页可以稍后持久化
```

这是理解顺序的示意，不是每条修改的完整源码流程。部分数据页也可能提前写回，只要它们对应的 WAL 已经持久化。

最重要的约束是：**不能让某次修改的数据页已经落盘，而恢复它所需的相关日志还只留在易失内存里。**

## 提交后突然断电会怎样

假设日志已经持久化，数据库告诉你提交成功，但某个索引页还没有写回文件。这时发生断电：

1. 内存中的新索引页丢失。
2. 重启时，数据库从合适的恢复位置读取 WAL。
3. 根据日志，把需要补做的修改重做到数据页。

这个动作叫 redo，重做。恢复不是简单地“所有出现过的记录都是已提交数据”；还要结合事务状态与可见性规则。

## 与第14题的关系

插入向量可能同时影响表记录、图节点、邻接边和元信息。崩溃后，这些内容不能恢复成彼此矛盾的状态。

如果把图直接交给外部 ANN 库写入另一个文件，PostgreSQL 并不会自动为它补齐恢复保障。需要明确该文件修改如何与数据库事务、日志和恢复协作。

重启后扩展能够加载，只证明没有立即启动失败；还要检查已提交记录、撤销记录、图结构，以及搜索行为是否符合要求。本项目尚未因此通过恢复实验。

## 易混淆点

- WAL 不是普通的调试日志，也不是把 SQL 文本保存下来就足够。
- WAL 不单独负责回滚；事务状态、MVCC 等机制也参与正确性。
- 同步提交通常等待日志持久化，不要求所有修改过的数据页在提交前都写回。
- 异步提交、关闭可靠持久化选项等会改变故障保障；不能通过削弱保障来宣称满足本题恢复要求。
