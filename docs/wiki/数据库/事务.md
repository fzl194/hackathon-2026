# 事务：把一组操作作为整体完成

[返回 Wiki 首页](../README.md) · [第14题全貌](../第14题全貌.md)

**一句话：事务把一组数据库操作组织成一个整体，通过提交确认，通过回滚撤销。**

## 为什么需要事务

假设一次转账需要两步：A 账户减100，B 账户加100。只做完一步就断电，会导致钱凭空减少或增加。

事务要求这些业务数据修改要么一起生效，要么一起取消。你可以先类比“尝试完成一次状态转换，失败就不能暴露半成品”；数据库还要把这个保证扩展到并发与崩溃。

## 一个向量记录的例子

假设已经有 `documents` 表，以下只演示事务语义：

```sql
BEGIN;
INSERT INTO documents (id, embedding)
VALUES (42, '[1, 2, 3]'::vector);
ROLLBACK;
```

`BEGIN` 开始事务，`ROLLBACK` 取消它。如果此前没有编号42，事务结束后，它不能作为有效记录被查询返回。

如果把 `ROLLBACK` 换成 `COMMIT`，就是确认这次修改。其他会话仍要根据各自查询快照判断能否看到它，并非所有正在运行的查询立即切换到新状态。

PostgreSQL 中，即使没有显式写 `BEGIN`，每条语句仍在事务中运行；常见的自动提交模式会让每条成功语句单独提交。

## ACID 的四个字母

|性质|直觉|需要留意|
|---|---|---|
|原子性 Atomicity|这组业务修改要么完成，要么取消|不意味着磁盘上的每个字节立即恢复原样|
|一致性 Consistency|从合法状态进入合法状态|数据库约束与应用业务逻辑都要正确|
|隔离性 Isolation|并发操作遵守规定的相互可见规则|不同隔离级别保证不同，不是一律串行执行|
|持久性 Durability|确认提交的修改应能抵抗故障丢失|保障依赖持久化配置及可靠存储|

MVCC、锁、WAL 等机制共同实现这些要求。不能认为“有 WAL 就已经完成所有 ACID”。

## 与第14题的关系

假设插入向量时，表里增加一条记录，图索引里也增加节点与边。随后事务回滚：

1. 查询不能把该记录当作有效答案。
2. 索引内部即使暂时残留结构，也不能破坏后续搜索与维护。
3. 不能为了清除一个节点，就让其他合法节点变得不可达或造成结构损坏。

所以“回滚后没有搜索到这条记录”只是必要检查之一，还需要验证其他记录、并发和恢复都正常。本页示例是学习材料，不代表项目已经通过这些测试。

## 易混淆点

- ANN 可以漏掉一部分合法近邻，但返回已回滚的插入记录是事务错误。
- 回滚不等于立刻清掉全部物理痕迹；记录是否可见与空间何时回收是两件事。
- PostgreSQL 的序列计数等有特殊规则，事务回滚也可能留下编号空洞；不能要求所有附带状态完全倒退。
