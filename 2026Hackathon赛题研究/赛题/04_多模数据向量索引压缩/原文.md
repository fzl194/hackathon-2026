**多模数据向量索引压缩**

## **二、背景信息（赛题产生的业务背景）：**

**大模型训练需要从海量真实数据中高效筛选和挖掘有效场景样本，用于模型迭代、长尾问题发现及场景泛化能力提升等。业务将图片、视频帧等多模态内容编码为高维向量，并通过近邻检索等方法完成相似样本发现、数据去重、困难样本挖掘和训练数据回流等操作。**

**业务数据体量持续高速增长，月度新增数据量可达2～3亿条，整体存量数据已进入EB级规模。海量、高维、持续增量的数据特征，对向量的构建效率、索引体积、内存占用、检索速度等提出了极高要求。**

**本赛题期望探索更高压缩率的向量编码、更紧凑的导航结构以及面向SSD和SIMD的检索策略，在严格空间预算下维持召回率90%(top10)和查询延迟600ms的要求。**

## **三、问题描述（现状、技术挑战等）：**

业务将图片、视频帧统一转换为 1024 维 FP32 高维向量，并与结构化标量元数据统一入库存储，支持向量与标量混合检索。为聚焦核心算法挑战，本次决赛仅评测纯向量 Squared L2 Top-K 检索，不评测标量过滤。

### 3.1当前业界示例方案一：IVF\_HNSW\_SQ8

当前向量检索索引采用 IVF、HNSW 与 SQ8 的组合思路：IVF 负责空间分桶，HNSW 可用于加速质心或图导航，SQ8 通过每维 8bit 标量量化压缩向量。IVF\_HNSW\_SQ8 通常是工程组合名称，并非 Faiss 或 Milvus 中唯一固定的标准索引类型。

1024 维 FP32 向量SQ8理论编码规模：

- 原始 FP32：4096 bytes/vector。
- SQ8 量化码：1024 bytes/vector，约为 FP32 的 1/4。
- 1 亿条：原始向量约 409.6GB；通过SQ8 量化后约 102.4GB。
- 1,000 万条正式终评集：原始向量约 40.96GB；通过SQ8 量化码约 10.24GB。

开源公开实现能够提供约 4:1 的 SQ8 向量编码压缩，并通过 IVF/HNSW 调整 Recall 与延迟。开源参考：

- Faiss 代码社区：https://github.com/facebookresearch/faiss
- Faiss Index Factory：https://github.com/facebookresearch/faiss/wiki/The-index-factory
- Milvus IVF\_SQ8：https://milvus.io/docs/ivf-sq8.md
- Milvus HNSW\_SQ：https://milvus.io/docs/hnsw-sq.md
- HNSW 论文：https://arxiv.org/abs/1603.09320

### 3.2当前业界示例方案二：AlayaLaser / RaBitQ 高压缩路线

候选替代方案引入 AlayaLaser 类磁盘图检索架构，利用 PCA 主成分与残差分解和RaBitQ高压缩向量编码组件降低内存。另外，可通过SIMD并行距离计算（精排），并结合SSD图遍历、节点缓存和搜索策略优化等提升检索性能。

预计可达到效果：

- 1 亿条：原始向量约 400GB，RabitQ + PCA 路线预计压缩至约10GB左右，即约 100 bytes/vector。
- 1,000 万条：比赛采用小数据集，等比例目标约为 1000MB，对应本赛题准入上限。
- 若要达到空间满分，还需进一步压缩至 600MB，即 60 bytes/vector。

方案思路可作为参考，开源与论文参考：

- AlayaLaser 论文：https://arxiv.org/abs/2602.23342
- AlayaLite 代码社区：https://github.com/AlayaDB-AI/AlayaLite
- RaBitQ-Library：https://github.com/VectorDB-NTU/RaBitQ-Library
- RaBitQ 文档：https://vectordb-ntu.github.io/RaBitQ-Library/
- DiskANN 代码社区：https://github.com/microsoft/DiskANN
- DiskANN 论文：https://arxiv.org/abs/1907.03390

### 3.3接口定义

- 主办方提供的数据集均为 **1024 维 FP32**；这是统一的数据交换格式，不是对选手内部实现精度的限制。选手可在构建与搜索内部使用 **FP32、FP16、BF16、INT8、SQ、PQ、RaBitQ、二值编码或混合精度**，也可自行降维、旋转和量化。
- 主办方提供的测试集，查询传入的数据为FP32格式。
- 返回值需要包含query检索结果top10的ID。

提交包要求：

1. 不允许符号链接、硬链接、绝对路径依赖或链接到提交包之外的文件。
2. 解压后的 index/ 目录是空间计量对象，必须不超过1000M；压缩包大小不作为索引空间成绩。
3. search.sh 必须可执行；运行日志只能写入stderr，不得向stdout 输出协议以外的内容。
4. search.sh 的文件名和命令行参数由选手按模板提供，但帧读写逻辑必须使用主办方模板，不能各队自行设计文本协议、HTTP 接口或结果文件格式。选手只实现“加载索引”和“对一条 query 返回 Top10”两个函数
5. 依赖必须在评委规定的离线环境中可安装或随提交包提供；终评期间不开放外部网络。
6. 选手必须提交 index\_manifest.json。它不是检索输入，而是索引装箱单，用来在启动 search.sh 之前确认上传文件完整、未被损坏、对应官方同一版 Final-10M base。

#### 3.3.2索引清单

index\_manifest.json 的主要作用是**校验选手上传索引是否正确、完整、未损坏**。评委回收赛题后只有数小时，无法重新构建索引，因此必须先用清单做静态检查，再启动检索。

index\_manifest.json 至少包含：

|  |
| --- |
| {   "schema\_version": "1.1",   "algorithm": "team\_algorithm\_name",   "dataset\_name": "vdbbench-10m-l2-1024",   "dataset\_version": "v1.0",   "dataset\_manifest\_sha256": "<官方 final\_10m/manifest.json 的 SHA-256>",   "base\_count": 10000000,   "dim": 1024,   "metric": "squared\_l2",   "internal\_dtype": "fp16|sq8|pq|rabitq|mixed|other",   "index\_bytes": 0,   "seed": 42,   "files": [     {"path": "index/graph.bin", "bytes": 0, "sha256": "<sha256>"}   ] } |

选手应使用官方脚本生成，不要手写哈希：

|  |
| --- |
| python3 tools/make\_index\_manifest.py \   --index-dir ./submission/index \   --dataset-manifest /data/contest/final\_10m/manifest.json \   --algorithm team\_algorithm\_name \   --internal-dtype rabitq \   --seed 42 \   --output ./submission/index\_manifest.json |

评委校验顺序：

1. 解压提交包后，确认存在 index/ 和 index\_manifest.json。缺少任一文件，直接判提交失败。
2. 读取清单，检查 schema\_version、dataset\_name、dataset\_version、base\_count=10000000、dim=1024、metric=squared\_l2。字段缺失或与官方数据不一致，停止评测。
3. 用官方 final\_10m/manifest.json 重算 SHA-256，必须等于 dataset\_manifest\_sha256。不相等说明索引不是针对本版 Final-10M base 构建。
4. 禁止符号链接、硬链接、绝对路径和 index/ 目录外路径。files[].path 必须位于 index/ 之下。
5. 对清单中每个文件检查：磁盘上存在、实际字节数等于 bytes、实际 SHA-256 等于声明值。任一文件缺失、大小不符或哈希不符，视为损坏或漏传。
6. 扫描实际 index/：磁盘上多出清单未声明的文件，或清单声明了磁盘上不存在的文件，均判失败。
7. 递归统计 index/ 实际字节数，作为空间成绩。该值必须不超过 800MB，并应与 index\_bytes 一致；不一致时以评委实测为准，并记录差异。
8. 上述静态检查全部通过后，才安装依赖并启动 search.sh。加载失败或无法返回合法结果，仍按提交失败处理，评委不补文件、不重建索引。

该清单不参与 Recall 和延迟计算，只决定提交包能否进入检索评测。

 

#### 3.3.3 config.json 与依赖文件

config.json 是给**选手自己的搜索程序**读取的冻结参数，不是评委用来调参的文件。评委只把路径传给 search.sh，不读取、不修改 params。

必填字段只有 4 个：

|  |
| --- |
| {   "schema\_version": "1.1",   "algorithm": "team\_algorithm\_name",   "seed": 42,   "params": {     "nprobe": 64,     "ef\_search": 128   } } |

 

|  |  |  |
| --- | --- | --- |
| **字段** | **谁使用** | **说明** |
| schema\_version | 评委 | 固定 "1.1"，用于确认文件格式 |
| algorithm | 评委归档 | 队伍算法名称，不影响评分 |
| seed | 选手程序 | 搜索中若有随机过程，必须固定该种子 |
| params | 仅选手程序 | 任意 JSON 对象；字段名和含义由选手自行定义 |

params 没有统一参数表。IVF 可以写 nprobe，HNSW 可以写 ef\_search，其他算法写自己的参数。若全部参数已经固化在索引文件中，params 必须写空对象 {}，不能省略该字段。提交后不得针对隐藏 query 修改此文件。

requirements.txt 是 Python 依赖清单，每行一个可安装的包及版本，例如：

|  |
| --- |
| numpy==1.26.4 faiss-cpu==1.8.0 |

评委在离线环境中执行 python3 -m pip install -r requirements.txt。它不是评分文件，也不描述算法参数。搜索程序为自包含二进制且没有 Python 依赖时，提交只含一行注释 # no python dependencies 的文件。使用 Conda 或容器时，改为提交 environment.yml 或 Dockerfile 其中之一，并在 README 说明，不再同时要求 requirements.txt。

#### 3.3.6退出码

通用退出码：0 成功，1 参数或格式错误，2 索引加载失败，3 运行时搜索失败。

#### 3.3.7评委流程

准备隐藏 query 与隐藏 GT  
 → 解压提交包，校验目录、数据集版本、索引 SHA-256  
 → 递归统计 index/，执行2000M准入检查  
 → 确保原始 base 不挂载、GT 对选手进程不可见  
 → 启动 search.sh（记录索引加载时间与增量 RSS）  
 → 随机顺序逐条发送隐藏 query，重复 1 轮  
 → 校验响应并计算 Recall@10、p50/p95   
 → 准入检查与排名

#### 3.3.8 公平性约束

- PCA / SQ8 / PQ / RaBitQ / IVF 等训练不得使用隐藏 query。
- 不限制选手内部数值精度，但不得通过保留或回读官方 base 绕过索引空间限制。
- 最终索引必须在提交截止前由选手自行构建并上传；评委不重建、不调参、不替换文件。
- 不得访问隐藏 GT、外部网络或评委机上的其他提交目录。
- 所有公开制品带 SHA-256；评委机校验后再跑。

| Recall@10     = 返回 Top10 与真值 Top10 的交集比例（平均） bytes/vector  = 索引总字节 / 向量条数 build\_sec     = 建索引时间 batch1\_p95\_ms = batch=1 查询延迟 p95（先预热） |

#### 5.1.6真值怎么对比（GT）

GT（Ground Truth）= 对每个 query 在全量 base 上精确算出的最近邻 ID。

Recall@10(q) = |选手返回的 Top10 ∩ 真值 Top10| / 10

对所有 query 取平均。真值文件里虽有 Top-100，计分时**只取前 10 个**与选手返回对比。

## **七、评选标准（如评分维度，分成几档等）：**

先执行硬门槛：

1. Recall@10 ≥ 90%。
2. batch=1、concurrency=1，p95 ≤ 600ms
3. 索引完整、接口可运行、结果 ID 合法且无重复。
4. 解压后的 index/ 不超过 2000MB。
5. 搜索阶段不读取原始 base、隐藏 GT 或网络资源。

通过硬门槛后，空间项按以下公式评分：

M 为解压后 index/ 大小，单位 MB：

M ≤ 600 → 100 分

600 < M ≤ 2000 → 100 - (M - 600) / 35

M > 2000 → 不准入

600MB 及以下得 100 分，正好 2000MB 得 60 分，中间线性计算。例如 1300MB 得 80 分。

构建时间由选手自报，仅作技术分析，不参与终评评分。
