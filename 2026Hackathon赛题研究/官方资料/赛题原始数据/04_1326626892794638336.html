多模数据向量索引压缩

二、背景信息（赛题产生的业务背景）：

大模型训练需要从海量真实数据中高效筛选和挖掘有效场景样本，用于模型迭代、长尾问题发现及场景泛化能力提升等。业务将图片、视频帧等多模态内容编码为高维向量，并通过近邻检索等方法完成相似样本发现、数据去重、困难样本挖掘和训练数据回流等操作。

业务数据体量持续高速增长，月度新增数据量可达2～3亿条，整体存量数据已进入EB级规模。海量、高维、持续增量的数据特征，对向量的构建效率、索引体积、内存占用、检索速度等提出了极高要求。

本赛题期望探索更高压缩率的向量编码、更紧凑的导航结构以及面向SSD和SIMD的检索策略，在严格空间预算下维持召回率90%(top10)和查询延迟600ms的要求。

三、问题描述（现状、技术挑战等）：

业务将图片、视频帧统一转换为 1024 维 FP32 高维向量，并与结构化标量元数据统一入库存储，支持向量与标量混合检索。为聚焦核心算法挑战，本次决赛仅评测纯向量 Squared L2 Top-K 检索，不评测标量过滤。

3.1 当前业界示例方案一：IVF_HNSW_SQ8

当前向量检索索引采用 IVF、HNSW 与 SQ8 的组合思路：IVF 负责空间分桶，HNSW 可用于加速质心或图导航，SQ8 通过每维 8bit 标量量化压缩向量。IVF_HNSW_SQ8 通常是工程组合名称，并非 Faiss 或 Milvus 中唯一固定的标准索引类型。

1024 维 FP32 向量SQ8理论编码规模：

  • 原始 FP32：4096 bytes/vector。
  • SQ8 量化码：1024 bytes/vector，约为 FP32 的 1/4。
  • 1 亿条：原始向量约 409.6GB；通过SQ8 量化后约 102.4GB。
  • 1,000 万条正式终评集：原始向量约 40.96GB；通过SQ8 量化码约 10.24GB。

开源公开实现能够提供约 4:1 的 SQ8 向量编码压缩，并通过 IVF/HNSW 调整 Recall 与延迟。开源参考：

  • Faiss 代码社区：https://github.com/facebookresearch/faiss
  • Faiss Index Factory：https://github.com/facebookresearch/faiss/wiki/The-index-factory
  • Milvus IVF_SQ8：https://milvus.io/docs/ivf-sq8.md
  • Milvus HNSW_SQ：https://milvus.io/docs/hnsw-sq.md
  • HNSW 论文：https://arxiv.org/abs/1603.09320

3.2 当前业界示例方案二：AlayaLaser / RaBitQ 高压缩路线

候选替代方案引入 AlayaLaser 类磁盘图检索架构，利用 PCA 主成分与残差分解和RaBitQ高压缩向量编码组件降低内存。另外，可通过SIMD并行距离计算（精排），并结合SSD图遍历、节点缓存和搜索策略优化等提升检索性能。

预计可达到效果：

  • 1 亿条：原始向量约 400GB，RabitQ + PCA 路线预计压缩至约10GB左右，即约 100 bytes/vector。
  • 1,000 万条：比赛采用小数据集，等比例目标约为 1000MB，对应本赛题准入上限。
  • 若要达到空间满分，还需进一步压缩至 600MB，即 60 bytes/vector。

方案思路可作为参考，开源与论文参考：

  • AlayaLaser 论文：https://arxiv.org/abs/2602.23342
  • AlayaLite 代码社区：https://github.com/AlayaDB-AI/AlayaLite
  • RaBitQ-Library：https://github.com/VectorDB-NTU/RaBitQ-Library
  • RaBitQ 文档：https://vectordb-ntu.github.io/RaBitQ-Library/
  • DiskANN 代码社区：https://github.com/microsoft/DiskANN
  • DiskANN 论文：https://arxiv.org/abs/1907.03390

3.3.2 索引清单

index_manifest.json 的主要作用是校验选手上传索引是否正确、完整、未损坏。评委回收赛题后只有数小时，无法重新构建索引，因此必须先用清单做静态检查，再启动检索。

index_manifest.json 至少包含：

{
  "schema_version": "1.1",
  "algorithm": "team_algorithm_name",
  "dataset_name": "vdbbench-10m-l2-1024",
  "dataset_version": "v1.0",
  "dataset_manifest_sha256": "<官方 final_10m/manifest.json 的 SHA-256>",
  "base_count": 10000000,
  "dim": 1024,
  "metric": "squared_l2",
  "internal_dtype": "fp16|sq8|pq|rabitq|mixed|other",

    {"path": "index/graph.bin", "bytes": 0, "sha256": "<sha256>"}

选手应使用官方脚本生成，不要手写哈希：

  --index-dir ./submission/index \

  --seed 42 \
  --output ./submission/index_manifest.json

评委校验顺序：

  1. 解压提交包后，确认存在 index/ 和 index_manifest.json。缺少任一文件，直接判提交失败。
  2. 读取清单，检查 schema_version、dataset_name、dataset_version、base_count=10000000、dim=1024、metric=squared_l2。字段缺失或与官方数据不一致，停止评测。
  3. 用官方 final_10m/manifest.json 重算 SHA-256，必须等于 dataset_manifest_sha256。不相等说明索引不是针对本版 Final-10M base 构建。
  4. 禁止符号链接、硬链接、绝对路径和 index/ 目录外路径。files[].path 必须位于 index/ 之下。
  5. 对清单中每个文件检查：磁盘上存在、实际字节数等于 bytes、实际 SHA-256 等于声明值。任一文件缺失、大小不符或哈希不符，视为损坏或漏传。
  6. 扫描实际 index/：磁盘上多出清单未声明的文件，或清单声明了磁盘上不存在的文件，均判失败。
  7. 递归统计 index/ 实际字节数，作为空间成绩。该值必须不超过 800MB，并应与 index_bytes 一致；不一致时以评委实测为准，并记录差异。
  8. 上述静态检查全部通过后，才安装依赖并启动 search.sh。加载失败或无法返回合法结果，仍按提交失败处理，评委不补文件、不重建索引。

该清单不参与 Recall 和延迟计算，只决定提交包能否进入检索评测。

def read_exact(stream, n):
    buf = stream.read(n)
    if not buf:
        return b""
    while len(buf) < n:
        chunk = stream.read(n - len(buf))
        if not chunk:
            raise EOFError("truncated frame")
        buf += chunk
    return buf

def main():
    ap = argparse.ArgumentParser()
    ap.add_argument("--index-dir", required=True)
    ap.add_argument("--config", required=True)
    ap.add_argument("--threads", type=int, required=True)
    args = ap.parse_args()
    config = json.load(open(args.config, "r", encoding="utf-8"))
    index = load_index(args.index_dir, config, args.threads)
    sys.stdout.buffer.write(READY)
    sys.stdout.buffer.flush()
    stdin = sys.stdin.buffer
    stdout = sys.stdout.buffer
    while True:
        head = read_exact(stdin, HEADER.size)
        if not head:
            return 0
        request_id, nq, dim, topk = HEADER.unpack(head)
        if nq != 1 or dim != 1024 or topk != 10:
            return 1
        query = struct.unpack("<" + "f" * dim, read_exact(stdin, 4 * dim))
        ids, distances = search_one(index, query, topk, config)
        stdout.write(struct.pack("<IiII", request_id, 0, 1, 10))
        stdout.write(struct.pack("<" + "I" * 10, *ids))

5.1.5 要看的指标

Recall@10     = 返回 Top10 与真值 Top10 的交集比例（平均）
bytes/vector  = 索引总字节 / 向量条数
build_sec     = 建索引时间
batch1_p95_ms = batch=1 查询延迟 p95（先预热）

5.1.6 真值怎么对比（GT）

GT（Ground Truth）= 对每个 query 在全量 base 上精确算出的最近邻 ID。

Recall@10(q) = |选手返回的 Top10 ∩ 真值 Top10| / 10

对所有 query 取平均。真值文件里虽有 Top-100，计分时只取前 10 个与选手返回对比。

#!/usr/bin/env python3
"""开发态评测：Recall@10、bytes/vector、构建时间、batch1 延迟。"""
import argparse, struct, time, os
import numpy as np
import faiss

def read_fbin(path):
    with open(path, "rb") as f:
        n, d = struct.unpack("<II", f.read(8))
        return np.fromfile(f, dtype=np.float32, count=n*d).reshape(n, d)

def read_gt(path):
    with open(path, "rb") as f:
        nq, k = struct.unpack("<II", f.read(8))
        return np.fromfile(f, dtype=np.uint32, count=nq*k).reshape(nq, k)

def recall_at_k(gt, ann, k=10):
    hits = sum(len(set(gt[i,:k]) & set(ann[i,:k])) for i in range(len(ann)))
    return hits / (len(ann) * k)

ap = argparse.ArgumentParser()
ap.add_argument("--base", default="/data/contest/dev_1m/base.fbin")
ap.add_argument("--query", default="/data/contest/dev_1m/query.fbin")
ap.add_argument("--gt", default="/data/contest/dev_1m/groundtruth.ibin")
ap.add_argument("--index-out", default="/data/contest/dev_1m/index.faiss")
ap.add_argument("--nlist", type=int, default=4096)
ap.add_argument("--nprobe", type=int, default=64)
ap.add_argument("--topk", type=int, default=10)
args = ap.parse_args()

base, query = read_fbin(args.base), read_fbin(args.query)
gt = read_gt(args.gt)

# ===== 示例：FAISS IVF+SQ8；赛题请替换为自有算法 =====
quantizer = faiss.IndexFlatL2(1024)
index = faiss.IndexIVFScalarQuantizer(quantizer, 1024, args.nlist, faiss.Metric_L2)

t0 = time.perf_counter()
index.train(base)
index.add(base)
faiss.write_index(index, args.index_out)
build_sec = time.perf_counter() - t0
index_bytes = os.path.getsize(args.index_out)

index.nprobe = args.nprobe
index.search(query[:50], args.topk)

_, I = index.search(query, args.topk)
recall = recall_at_k(gt, I, args.topk)

lats = []
for i in range(len(query)):
    t0 = time.perf_counter()
    index.search(query[i:i+1], args.topk)
    lats.append((time.perf_counter() - t0) * 1000)
lats = np.asarray(lats)

print("=== dev metrics ===")
print(f"N={len(base)} dim=1024 metric=squared_l2")
print(f"Recall@{args.topk}={recall:.6f}")
print(f"index_bytes={index_bytes}")
print(f"bytes_per_vector={index_bytes/len(base):.2f}")
print(f"build_sec={build_sec:.3f}")
print(f"batch1_p50_ms={np.percentile(lats,50):.3f}")
print(f"batch1_p95_ms={np.percentile(lats,95):.3f}")

步骤 4：构建 Final-10M 最终索引（必做）

主办方赛前开放 Final-10M base 和 manifest.json，但不开放隐藏 query/GT。选手必须在提交截止前自行完成最终索引构建；评委终评不执行构建脚本。

1. 下载并校验 final_10m/base-*.fbin 和 manifest.json
2. 读取全部 10 个 base 分片，使用已冻结参数构建索引
3. 将搜索所需的全部文件写入 submission/index/
4. 若提供公开 query/GT，先在 10M 上自测 Recall、空间与延迟
5. 生成 index_manifest.json 并运行官方接口校验工具

注意：

  • 最终索引必须对应官方 manifest.json 指定的同一版 Final-10M base 和 ID 顺序。
  • 不能用 Dev GT 评测 Final-10M；base 集合变化后精确近邻也会变化。
  • 构建产生的临时文件不要放入 submission/index/。
  • 上传前必须确认脱离原始 base 后，search.sh 仍能独立完成检索。

七、评选标准（如评分维度，分成几档等）：

先执行硬门槛：

  1. Recall@10 ≥ 90%。
  2. batch=1、concurrency=1，p95 ≤ 600ms
  3. 索引完整、接口可运行、结果 ID 合法且无重复。
  4. 解压后的 index/ 不超过 2000MB。
  5. 搜索阶段不读取原始 base、隐藏 GT 或网络资源。

通过硬门槛后，空间项按以下公式评分：

M 为解压后 index/ 大小，单位 MB：

M ≤ 600 → 100 分

600 < M ≤ 2000 → 100 - (M - 600) / 35

M > 2000 → 不准入

600MB 及以下得 100 分，正好 2000MB 得 60 分，中间线性计算。例如 1300MB 得 80 分。

构建时间由选手自报，仅作技术分析，不参与终评评分。
