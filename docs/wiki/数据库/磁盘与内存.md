# 磁盘与内存：为什么O(1)访问也可能很慢

[Wiki首页](../README.md) · 前置：[HNSW](../算法/HNSW.md) · 下一页：[DiskANN与Vamana](../算法/DiskANN与Vamana.md)

数据不在内存时，访问一个节点可能要等待SSD。算法既要减少计算，也要考虑读多少数据、怎样读、能否复用与并行。

## 用算法选手熟悉的视角理解

数组下标访问在抽象模型里可看成O(1)，但这里还要问：在CPU缓存、内存，还是需要从磁盘读取？不同层的代价并不相同。

下面只是直觉拆分，不是精确公式：

```text
查询成本 ≈ 距离计算 + 无法被缓存/并行掩盖的I/O等待
         + 数据库处理 + 并发协调
```

少计算一些，但每一步都要等随机读盘的方案，可能输给多计算一些、读取更连续的方案。

## 四个需要区分的概念

|概念|直觉|
|---|---|
|顺序读与随机读|连续搬一段数据，还是到分散的位置取数据？|
|缓存|已经读过的数据，能否下次直接在内存用？|
|页/块布局|一次读取的一块数据里，有多少内容真的有用？|
|并发I/O|能否同时发出多个读取，减少总等待？|

操作系统文件缓存、数据库缓冲区、算法自己的缓存都可能占内存。不能只统计某个小数组就认定符合比赛内存上限；具体计量以评测器为准。

## 先做空间算术

- 10亿×128维×float32的纯坐标为512GB。
- BIGANN上游原始uint8坐标，同规模载荷为128GB；导入float32后会膨胀。
- 100万×3072维×float32为12.288GB。
- 一个3072维float32向量为12,288字节，约12KiB，超过PG常见8KiB页面。

GB按10的9次方字节计算，KiB按1024字节计算。这些只是坐标载荷，不含表、图边、元数据、WAL和临时空间。

## 能存下与能建索引不同

PG表的大字段机制可以存储超过单页的值，不代表任意索引格式能把完整向量和邻接信息放进一个节点页。存储类型上限、具体索引维度上限和整体资源上限需要分开。

## 与本题的关系

必须测量数据和索引明显超内存时的行为，记录CPU、SSD、内存与缓存条件。小数据全驻内存的高QPS，不能证明磁盘方案高效。
