# HNSW参数与构建代价

[Wiki首页](../README.md) · 前置：[HNSW插入与选边手推](HNSW插入与选边手推.md)、[HNSW查询手推](HNSW查询手推.md)

先分清三个预算：M控制连接，efConstruction控制构建搜索中的候选保留范围，efSearch控制用户查询时的候选保留范围。它们不是同一个参数的三种名字。

## 1. 用招聘类比区分前两个预算

可以把构建搜索理解为收集候选，选边理解为最终留下一部分连接：efConstruction扩大构建阶段的候选保留范围，M限制最终连接预算。

这个类比不意味着efConstruction就是整次搜索面试的总人数。构建搜索会不断发现和淘汰候选，累计距离计算或访问的节点数可以超过它。

|参数|发生阶段|主要控制|通常代价|
|---|---|---|---|
|M|构图/维护|新点选边和图连接规模，具体容量依层与实现|图更大，更多邻接访问和维护工作|
|efConstruction|构图/插入|搜索邻居时较好候选集的容量|更充分的构建搜索，常增加构建耗时|
|efSearch，hnswlib名为ef|用户查询|查询搜索时较好候选集的容量|常提高召回，但增加查询工作|

改变查询ef通常无需重建索引。增加efConstruction不会自动重新修好已经建成的全部旧图；M和构建参数的效果需要通过重建或相应维护过程落实，并比较实验。

## 2. 沿用插入X的例子

新点X=(0,0)，候选按距离为A、B、C、D、E，A和B在同一个很近的区域。设M=2：

|构建搜索假设返回的候选|按前页启发式选边|原因|
|---|---|---|
|只有A、B|只有A|B被A遮挡，该实现不强制补满|
|A、B、C、D、E|A、C|有机会发现另一个有用方向|

可以用efConstruction=2与5来理解较小、较大候选容量，但本表没有执行搜索，也不保证真实图上的这两个参数一定返回上述集合或全局最近几个点。

这说明M再大也无法选到没找到的候选；找到很多候选也不等于要把它们全连起来。候选发现与选边是两个阶段。

## 3. M不等于每点最终恰好M条边

此次读取的hnswlib新点每层先选择至多M个邻居，旧节点加入反向连接时，上层容量为M，底层容量为2M。筛选可能留下更少，后续插入还会改变邻接表。

源码初始化还会令有效efConstruction至少为M。以上是该实现的具体行为，不能直接断言所有HNSW库和PG扩展都完全相同。

## 4. 为什么参数不是越大越好

- M增加通常会扩大邻接表，影响内存、磁盘布局和每次扩展的扫描成本。
- efConstruction增加可能改善构图，但有耗时、临时工作空间和收益饱和问题。
- 查询ef增加允许更多探索，也可能增加距离计算和随机读盘。
- 构图若缺少关键连接，仅扩大查询预算不一定能以可接受成本补救。

这些是常见权衡，不是无需测量的收益保证。层次随机性、插入顺序、数据分布与具体实现同样重要。

## 5. 与第14题的关系

本题不只看查询，还考核构建时间、索引大小、内存和动态能力。应先固定M和efConstruction构建一份索引，再扫描查询ef形成曲线；比较不同构建配置时，要重新记录构建与资源代价。

图可持久化不等于适合超内存。邻居越多，究竟多读多少页、缓存能否命中、写入和WAL代价怎样，都需要在实际环境验证，而不是只报召回最高的一组参数。
