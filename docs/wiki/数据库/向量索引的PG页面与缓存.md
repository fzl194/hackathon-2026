# 向量索引的PG页面与缓存

[Wiki首页](../README.md) · 前置：[PostgreSQL与索引扩展](PostgreSQL与索引扩展.md)、[DiskANN内存与SSD查询手推](../算法/DiskANN内存与SSD查询手推.md) · 下一篇：[向量插入的事务与WAL手推](向量插入的事务与WAL手推.md)

把DiskANN思想放进PG，需要决定持久数据怎样存、图怎样通过数据库接口读写。本页采用一条教学路线：关键索引状态放进PG管理的索引关系页面。它是设计示意，尚未确定最终方案，也未实现、编译或运行。

## 1. 表与索引是两份不同的物理结构

表保存用户记录及行版本信息；索引保存导航与定位结构。可以先想成两本文件：一本存文章，一本存导航目录，不能把两者的页号混用。

PG通常以8KiB页管理表和索引，具体大小可由编译配置改变。假设已有documents表，列为id与embedding，并已建立研究中的向量索引：

```text
表的第37页、第5项：id=42，embedding=[0.1,0.2,0.3]，行版本信息

索引第0页：索引维度、入口、编码配置等元信息
索引第82页、第3项：节点N，指向表记录(37,5)，保存导航码与邻接引用
索引其他页面：本例所需的原向量副本及其他节点/元信息
```

这些页号、内容布局及编号均为人工示例，不对应真实运行的数据库。

|编号|作用|不要混淆|
|---|---|---|
|业务id=42|应用定义的标识|不是物理页地址|
|heap TID=(37,5)|在这张表中定位一个物理行版本|更新可能改变，清理后位置可能复用|
|索引内节点位置=(82,3)|定位图结构中的节点|不是表记录TID，需有安全的映射与回收规则|

N只是本页给节点起的名字，不强制实现再增加一个独立编号字段。

## 2. 本例为什么也在索引里保留原向量信息

为了把候选评分与最终行可见性分开，本例假设索引还能读取对应行版本的原向量副本。图搜索可以计算候选准确距离，最后普通索引扫描仍回表检查可见性。

这是空间与I/O的取舍，不是强制方案：也可以研究只保留表中原向量、需要重排时通过合适的表访问接口取值，但那会增加取表/大字段的成本与可见性处理。不能重复存向量却只统计表的一份空间。

索引副本必须对应具体行版本，不能用一个会被原地覆盖的业务id→向量缓存代替所有版本。

## 3. shared_buffers是PG的共享页缓存

读取索引第82页时，扩展可使用ReadBuffer等PG接口：命中共享缓冲区就复用内存中的页；未命中则由PG读取关系文件。底层还可能命中操作系统缓存，不能把PG缓存未命中都算成物理SSD读取。

```text
图搜索需要某节点
  → 定位它的索引页
  → PG共享页缓存
      ├── 命中：访问内存页
      └── 未命中：读取关系文件中的页
```

PG提供页缓存和读写设施，但不会自动知道哪几个图节点适合组成候选、哪种布局最省I/O。经典DiskANN的直接SSD读取与beam调度也不能原样当作PG缓冲接口已经实现的功能。

## 4. pin与内容锁分别解决什么

- pin：保证你使用的这块缓冲区不会被置换成另一页，不保证页内容不变。
- 页内容共享锁：协调安全读取。
- 页内容排他锁：协调修改，避免同时破坏页。

先取得pin，再按协议取得适当内容锁。用完后释放；不能保存一个已解除保护的裸指针，下一次仍假设它指向原来的稳定内容。

页面锁是短时结构保护，MVCC是行可见性规则。它们不能互相替代；同样，索引整体已有锁不等于两个写入者不能同时修改邻接表。

## 5. 额外算法缓存仍要自己设计

如果始终经PG缓冲读取规范页内容，可以复用缓冲管理；如果另外保存解码向量、整块PQ码或邻接表副本，就要设计更新、失效、版本、重建与内存预算。

PG常用多个后端进程服务连接。每个后端都复制一份全数据压缩码，可能把原本可接受的内存放大很多倍。共享表示、按需页访问或其他方式需实测权衡；PG页缓存并不保证全体短码永远常驻DRAM。

缓存应能从持久状态重建，不能是提交成功后数据仍存在的唯一依据。

## 6. 高维不会自动被索引TOAST解决

3072维float32坐标载荷为12,288字节，大于默认8KiB页，尚未计算页头和邻接表。表字段可利用TOAST等机制处理大值，不代表自定义索引项自动拥有同样的跨页能力。

索引需设计紧凑导航节点、独立向量区、分块引用或其他格式，处理跨页读取与恢复。维度能存入表，不等于索引格式与性能已经合格。

## 7. 哪些可复用，哪些不能直接拿来用

|部分|可复用基础|扩展仍要负责|
|---|---|---|
|类型、距离、SQL操作符|pgvector等既有能力，依版本和许可集成|所需类型×距离的索引支持与测试|
|关系文件、页读写、共享缓冲|PG存储与buffer manager|页格式、节点引用、布局与读取策略|
|并发设施|PG的锁与pin机制|锁粒度、顺序、结构发布与死锁分析|
|持久化|PG的WAL与恢复框架|为每类索引修改正确记录日志，设计恢复一致性|
|行可见性|PG快照与表访问路径|正确TID、扫描接口及不误返回非法记录|
|图与量化|算法或开源实现可供研究|适配PG状态、内存限制、增删改与目标指标|

外部索引文件也可以设计集成，但PG不会仅因文件被扩展打开就自动管理其缓存、日志、备份与事务。这里优先用PG页面讲清职责，不声称这是唯一方案。
