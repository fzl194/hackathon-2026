## 

NDS多路径IO分配、聚合与缓存提升算法

**决赛赛题来自技术领域：** 大模型推理基础设施、操作系统内核与高性能存储；涉及openEuler社区NDS（NPU Direct Storage）、Ascend NPU、NVMe RAID0及KVCache存储后端。

**赛题限制：**

- 赛题面向外部开源社区和高校参赛者开放，不要求访问公司内部网络或保密数据。
- 主办方提供公开的NDS代码、确定性事件评测框架、公共样例Trace、固定资源参数及实测性能桶。
- 正式评测使用隐藏Trace；参赛程序不能访问外部服务，也不能提前获得未来请求。
- 参赛程序最多使用8个CPU核、32个进程和16384MB内存；单次决策时间上限为60000ms。
- 可以使用开源算法库或求解器，但必须随方案提交完整构建说明并保证离线可复现。

## 二、背景信息

大模型推理过程中，KVCache容量可能超过HBM和DDR容量，需要将部分KVCache卸载到本地NVMe SSD。NDS在Ascend HBM与NVMe之间提供异步DMA数据通路，可绕过传统的“SSD → DDR → HBM”两阶段CPU中转路径，降低CPU参与开销并提高KVCache加载带宽。

NDS当前已经集成到LMCache-Ascend，并在面向大规模用户的Code Agent服务中经过长期部署验证。随着KVCache压缩、稀疏注意力和混合注意力的发展，KVCache IO呈现新的特征：

- 单次IO粒度持续减小；
- HBM地址、SSD偏移和长度可能无法满足512B对齐；
- 一个SSD连续区间可能需要写入多个离散HBM地址；
- 多个请求的SSD区间可能相邻，具备聚合读取机会；
- 小IO需要足够并发才能利用SSD、H2D、D2H和D2D带宽；
- HBM聚合缓冲区和DDR fallback池容量有限，需要分块和流水复用；
- DIRECT与SSD→DDR路径共享同一套RAID0存储资源，会互相影响实际带宽；
- 前台数据完成后，可以后台提升到KVCache内存池以服务后续访问，但PROMOTE本身也会消耗SSD或D2H资源以及CPU/NPU调用开销。

现有NDS缺少面向上述场景的统一自适应调度能力。简单规则，例如“对齐请求全部DIRECT、非对齐请求全部FALLBACK”，无法同时处理对齐扩展、聚合读放大、并发带宽、缓冲区占用、前后台资源竞争和未来缓存收益之间的组合优化。

本赛题希望从真实NDS业务中抽象出一个可公开、可复现的在线组合优化问题，推动参赛者设计兼顾解质量、求解速度和工程可落地性的多路径IO调度算法。

## 三、问题描述

### 3.1 IO模型

一个完整测试用例是一条按时间到达的io\_submit Trace。每次io\_submit最多包含1024个iocb，完整Trace可以包含任意多个io\_submit。

每个iocb描述：

- RAID0逻辑设备上的一个连续SSD读取区间；
- 同一张NPU卡上的一个或多个离散HBM目标区域；
- 当该iocb的全部前台数据完成后，通过IOCB\_COMPLETE事件体现io\_getevents完成语义。

参赛程序按时间接收当前已到达且未被KVCache内存池命中的请求，只能使用当前状态和历史信息，不能看到未来Trace。

### 3.2路径选择

调度器需要在以下路径中作出选择：

| **路径** | **数据流** | **主要约束与代价** |
| --- | --- | --- |
| DIRECT | SSD → HBM | 低CPU开销，但SSD地址、HBM地址和长度必须满足512B对齐 |
| AGGREGATE | SSD → 临时HBM → 目标HBM | 可处理非对齐和离散目标；产生对齐读放大，占用HBM缓冲区和D2D资源 |
| FALLBACK | SSD → fallback DDR → HBM | 适用于所有请求；占用最多1024MB的循环DDR池以及H2D资源 |
| PROMOTE\_SSD | SSD →KVCache内存池 | 前台完成后的后台提升；重新读取SSD并与前台SSD流量竞争 |
| PROMOTE\_HBM | 目标HBM →KVCache内存池 | 前台完成后的后台提升；不重读SSD，但占用D2H资源 |

PROMOTE不是当前iocb的前台完成路径。调度器在前台iocb完成后自主决定是否启动PROMOTE，上层不指定PROMOTE开始时间，也不发送启动命令。调度器实际启动PROMOTE时输出PROMOTE\_START记账事件，实际完成时输出PROMOTE\_COMPLETE事件。

### 3.3需要解决的子问题

参赛者需要同时完成：

**1. 路径分配：** 为每个iocb或其子区间选择DIRECT、AGGREGATE或FALLBACK，并在前台完成后决定是否PROMOTE及其来源路径。

**2. 拆分与聚合：** 决定一个iocb如何分块，哪些相邻SSD区间应组成AGGREGATE操作，以及如何控制对齐读放大。

**3.** **并发与流水：** 安排SSD、H2D、D2H和D2D传输的启动顺序。不同size和不同执行组可以重叠运行，只要满足硬资源约束。

**4. 共享带宽：** DIRECT、AGGREGATE的SSD阶段、FALLBACK的SSD→DDR阶段以及PROMOTE\_SSD共享nvme\_bw；并发变化会动态改变所有未完成传输的服务速率。

**5.** **资源复用：** HBM聚合缓冲区和fallback DDR池均可循环使用，总传输量可以超过池容量，但任意时刻的在途占用不能超过容量。

**6. 完成语义：** SCHEDULE\_DECISION不提前承诺最终完成时间。前台iocb和后台PROMOTE实际完成后，分别输出独立完成事件，由评测器复算和校验。

**7.** **缓存提升：** PROMOTE完成后缓存项才生效；KVCache内存池缓存由评测框架按固定容量、TTL和LRU规则维护。

### 3.4问题抽象

本题可以抽象为带有以下特征的在线资源受限组合调度问题：

- 每个数据区间存在多种执行路径；
- AGGREGATE允许多个区间组合，组合会改变命令数量、物理读取量和资源需求；
- 操作包含具有前后依赖的多阶段传输；
- 多类可再生资源和容量资源同时受限；
- 传输速率由当前活动操作集合、IO size性能桶和共享带宽共同决定；
- PROMOTE选择会消耗当前资源，并可能改变后续请求的处理路径；
- 目标函数同时考虑Trace时间、CPU成本和NPU调用成本。

### 3.5接口定义

评测框架与参赛程序使用JSON事件交互。

| **方向** | **事件** | **作用** |
| --- | --- | --- |
| 评测框架 → 调度器 | IO\_SUBMIT | 提供当前未命中的前台iocb和运行时状态 |
| 评测框架 → 调度器 | CACHE\_HIT | 提供由KVCache内存池处理的缓存命中状态变化 |
| 调度器 → 评测器 | SCHEDULE\_DECISION | 输出前台路径、数据覆盖、分块、依赖、优先级和最早启动时间 |
| 调度器 → 评测器 | PROMOTE\_START | 通知评测器PROMOTE已经由调度器自主启动，用于共享资源记账 |
| 调度器 → 评测器 | IOCB\_COMPLETE | 表示一个或多个前台iocb已完成 |
| 调度器 → 评测器 | PROMOTE\_COMPLETE | 表示一个或多个后台PROMOTE已完成 |

PROMOTE\_START只是运行状态通知，不是启动申请。评测器不决定PROMOTE是否开始，只根据该事件将PROMOTE负载计入SSD或D2H活动集合。

接口字段、事件顺序和完整JSON示例见附录F。

## 四、期望达到的指标和效果

### 4.1 功能目标

- 对全部未命中iocb形成无遗漏、无重复的完整数据覆盖；
- 正确处理512B对齐、对齐扩展、跨iov分块和跨iocb聚合；
- 支持DIRECT、AGGREGATE、FALLBACK及两种PROMOTE来源；
- 支持不同size、不同路径和多个执行组并发；
- 支持总数据量超过HBM/DDR临时池容量时的循环缓冲和流水执行；
- 正确输出IOCB\_COMPLETE、PROMOTE\_START和PROMOTE\_COMPLETE事件；
- 正确维护全局iocb、KVCache内存池缓存、TTL和LRU状态；
- 对相同输入和随机种子产生可复现结果。

### 4.2 优化目标

设：

T = TraceTime  
  
C = 完整Trace中前台操作、PROMOTE及KVCache内存池命中的CPUCost总和  
  
G = 完整Trace中前台操作、PROMOTE及KVCache内存池命中的NPUCost总和  
  
J = time\_cost\_per\_us × T + C + G

参赛程序需要最小化J。其中：

- T反映端到端时间和有效带宽；
- C惩罚过多逻辑SSD命令和CPU侧算子下发；
- G惩罚过多H2D、D2H和D2D调用；
- H2D、D2H和D2D传输时间已通过性能桶计入T，不在C或G中重复累计。

评测器同时报告前台有效带宽、P50/P95/P99 iocb时延、CPU总成本、NPU总调用成本、物理读放大率、PROMOTE命中率及驱逐次数，用于分析和同分比较。

### 4.3 性能和资源目标

- 在全部基础用例上输出可行方案；不可行Trace的优化得分为0。
- 在小规模用例上尽量接近精确最优或可证明下界。
- 在中、大规模隐藏Trace上，在60000ms单次决策时限内稳定输出合法方案。
- 遵守8核CPU、32进程、16384MB内存上限。
- 重点提升非对齐、高碎片、混合size和资源压力场景下相对固定规则基线的综合成本与有效带宽。

## 七、评选标准

总分100分。

### 7.1可行性与正确性：20分

评测器检查：

- 数据是否完整且唯一覆盖；
- 路径、512B对齐、聚合、拆分和vector映射是否合法；
- 全局iocb、HBM、fallback DDR、KVCache内存池及复制并发约束是否满足；
- 混合size和共享带宽计算是否正确；
- IOCB\_COMPLETE、PROMOTE\_START和PROMOTE\_COMPLETE是否合法；
- 调度器报告的complete\_us是否与评测器复算一致；
- TTL、LRU和KVCache内存池命中状态是否一致；
- 输入输出格式以及运行资源限制是否满足。

某个Trace输出不可行时，该Trace优化得分为0。

### 7.2优化效果：60分

每个测试Trace计算：

CostRatio = J\_reference / J\_solution  
  
TraceScore = 60 × min(1, CostRatio)

小规模离线用例使用精确算法或可证明下界获得参考结果；中、大规模在线Trace使用比赛开始前冻结的在线参考算法结果。所有Trace按规模、非对齐率、碎片度、混合size比例和PROMOTE复用模式加权平均。超过参考方案的结果用于排行榜同分排序，正式优化分最高为60分。

### 7.3算法性能与可扩展性：10分

- 是否遵守8核、32进程和16384MB内存限制；
- 单批决策时间、峰值内存和大规模输入解析效率；
- 长Trace状态维护开销；
- 是否能在时限内持续输出合法方案。

### 7.4算法设计与可复现性：10分

- 算法说明和关键数据结构；
- 时间和空间复杂度分析；
- 路径选择、聚合、流水、混合size及PROMOTE策略；
- 构建运行说明、固定随机种子和自动化复现脚本。

### 7.5梯度用例

**-** **基础要求：** 对齐IO、单路径、低并发和基本完成事件；

**- 进阶要求：** 非对齐、多iov、AGGREGATE/FALLBACK分流和循环缓冲；

**-** **挑战要求：** 混合size、跨iocb聚合、前后台共享带宽、KVCache内存池缓存和对抗性Trace。

## A.1 iocb

| **字段** | **含义** |
| --- | --- |
| iocb\_id | iocb编号，在同一submit\_id中唯一 |
| opcode | IO类型，基础赛题固定为READV |
| device\_id | 目标NPU卡编号 |
| ssd\_offset | SSD连续读取范围的起始字节偏移 |
| length | SSD连续读取范围的总长度，单位为Byte |
| iovs | 离散HBM目标地址数组 |

## A.2 iov

| **字段** | **含义** |
| --- | --- |
| iov\_id | iov编号，在同一iocb中唯一 |
| hbm\_addr | 目标HBM虚拟地址 |
| length | 该HBM区间的数据长度，单位为Byte |

必须满足：

iocb.length = Σ iov.length

第k个iov对应的SSD起始位置为：

iocb.ssd\_offset + 前k-1个iov的length之和

## A.3子区间

参赛程序可以按照iocb\_offset把一个iocb拆成若干连续子区间。全部子区间必须对原始[0, iocb.length)形成无遗漏、无重叠的完整覆盖。子区间可以位于一个iov内部，也可以横跨相邻iov。

## A.4 KVCache内存池缓存键

(device\_id, ssd\_offset, length)

基础赛题只允许对完整iocb执行PROMOTE，不对iocb子区间单独建立缓存项。测试用例保证一个iocb的全部iov要么完整命中，要么完全未命中。

# 附录B：路径和缓存规则

## B.1 DIRECT

DIRECT执行SSD → HBM。其子区间必须同时满足SSD起始地址、对应HBM起始地址和传输长度均为512B的整数倍。DIRECT不占用HBM聚合缓冲区或fallback DDR池。

## B.2 AGGREGATE

AGGREGATE执行：

SSD → 临时HBM → 目标HBM

1. SSD范围向前、向后扩展到512B边界；
2. SSD→临时HBM使用DIRECT性能桶；
3. 临时HBM→目标HBM使用D2D性能桶；
4. 相关D2D全部完成后释放临时HBM。

同一AGGREGATE可以覆盖同一张NPU卡上来自一个或多个iocb的相邻SSD范围，也可以拆分成多个流水分块。总传输量可以超过hbm\_capacity，但任意时刻的临时HBM占用不得超过该容量。

## B.3 FALLBACK

FALLBACK执行：

SSD → fallback DDR → HBM

SSD范围向512B边界扩展；SSD→DDR使用相应性能桶，DDR→HBM使用H2D性能桶。DDR缓冲区在相关H2D完成后释放。fallback池固定为1024MB并可循环复用，因此累计传输量可以超过1GB。

## B.4 PROMOTE

PROMOTE只能在完整前台iocb完成后启动，不阻塞该iocb的IOCB\_COMPLETE。

- PROMOTE\_SSD：重新执行SSD → KVCache内存池，使用SSD→DDR性能桶，不占用fallback ddr\_capacity。
- PROMOTE\_HBM：执行目标HBM → KVCache内存池，使用D2H性能桶，不重新读取SSD。

调度器自主决定PROMOTE路径和启动时机。实际取得资源后输出PROMOTE\_START；完成后输出PROMOTE\_COMPLETE。只有完成事件通过校验后，缓存项才生效。

## B.5KVCache内存池缓存和驱逐

- kvcache\_pool\_used初始为0；
- 缓存项从PROMOTE完成时开始计时；
- promote\_ttl\_us = 60000000；
- 每次命中刷新最近命中时间；
- 空间不足时先驱逐超TTL项，再按LRU驱逐；
- 如果对象自身大于kvcache\_pool\_capacity，PROMOTE失败；
- 缓存表、容量、命中和驱逐结果以评测框架状态为准。

KVCache内存池命中请求不再进入NDS调度输入，由框架模拟KVCache内存池→HBM。该复制不受参赛程序控制，但作为外部活动负载计入对应NPU卡的H2D共享资源状态。

# 附录E：混合size和动态共享带宽

## E.1活动集合与执行组

group\_id只表示调度器组织的一批传输项，不表示资源独占，也不形成组间先后约束。不同执行组、不同路径和不同size可以同时运行。

对资源x：

A\_x(t) = {o | actual\_start\_us(o) ≤ t 且 remaining\_bytes(o,t) > 0}  
  
q\_x(t) = |A\_x(t)|

并发度由评测器根据所有已启动且未完成的活动项自动确定；参赛程序不能直接填写q或指定性能桶。

## E.2 SSD共享

SSD活动集合包括DIRECT、AGGREGATE的SSD→临时HBM、FALLBACK的SSD→DDR以及PROMOTE\_SSD。

对于活动SSD项o：

BW(o,t) = nvme\_bw × U(size(o), q\_SSD(t)) / q\_SSD(t)

其中DIRECT和AGGREGATE查询DIRECT桶；FALLBACK和PROMOTE\_SSD查询SSD→DDR桶。所有SSD项共享nvme\_bw。新操作开始或旧操作完成时，评测器重新计算全部未完成SSD项的带宽。

## E.3 H2D和D2H

H2D和D2H按NPU卡和方向分别建模：

BW\_H2D(o,t) = h2d\_bw × U(size(o), q\_H2D,c(t)) / q\_H2D,c(t)  
  
BW\_D2H(o,t) = d2h\_bw × U(size(o), q\_D2H,c(t)) / q\_D2H,c(t)

并满足对应复制并发上限。每个活动项按自身size匹配桶，但使用同卡、同方向的当前活动项总数匹配并发桶。

## E.4 D2D

BucketBW(o,t) = D2DBucket(size(o), q\_D2D,c(t))  
  
RawBW(o,t) = BucketBW(o,t) / q\_D2D,c(t)  
  
Scale(t) = min(1, d2d\_bw / ΣRawBW(o,t))  
  
BW(o,t) = RawBW(o,t) × Scale(t)

## E.5 桶匹配规则

1. SSD阶段按对齐扩展后的物理读取大小匹配size；复制阶段按有效复制量匹配size。
2. 混合size同时活动时，每个项独立匹配size bucket。
3. 大小位于两个bucket之间时，使用不超过该大小的最大bucket。
4. 并发度位于两个并发点之间时，使用不超过当前并发度的最大bucket。
5. 小于最小size时使用最小bucket；大于最大size时使用最大bucket。
6. 超过性能表最大并发测量值时使用最大并发bucket，但复制操作仍受硬并发上限约束。

## E.6事件驱动模拟

评测器按时间处理新IO\_SUBMIT、前台操作启动、PROMOTE\_START、各传输阶段完成、缓冲区释放、完成事件、缓存命中、TTL和LRU驱逐。

两个相邻事件之间活动集合不变：

RemainingBytes(o,t+Δt)  
  
  = RemainingBytes(o,t) - BW(o,t) × Δt

每次活动集合变化后重新计算并发度、性能桶和全部未完成项的带宽。完成时刻向上取整到整数微秒，评测器内部使用整数或有理数，避免浮点比较差异。

# 附录F：事件协议与输出约束

## F.1前台调度决策

每个逻辑传输项可包含：

- not\_before\_us：最早启动时间；
- depends\_on：必须先完成的传输项ID；
- priority：竞争硬资源时的优先级；
- group\_id：批量组织标识，不形成资源独占。

实际启动还必须满足阶段依赖、iocb名额、缓冲区容量以及H2D/D2H/D2D并发约束。SSD阶段没有独立硬并发上限；符合依赖的SSD项可以启动并与现有SSD操作共享带宽。

## F.2 完成事件

- SCHEDULE\_DECISION不包含最终complete\_us；
- 一个iocb所有必要前台阶段完成后，调度器输出IOCB\_COMPLETE；
- PROMOTE实际取得资源时，调度器输出PROMOTE\_START；
- PROMOTE全部传输完成后，调度器输出PROMOTE\_COMPLETE；
- 同一时刻完成的多个任务可以放入同一个completions数组；
- 同一个iocb或PROMOTE只能完成一次；
- PROMOTE\_COMPLETE不阻塞源iocb的IOCB\_COMPLETE；
- 评测器接受IOCB\_COMPLETE后释放相应iocb名额；
- 评测器接受PROMOTE\_COMPLETE后更新KVCache内存池缓存，并从complete\_us开始计算TTL。

调度器可以在PROMOTE\_START中给出estimated\_complete\_us用于运行观测；该值不是最终承诺，也不影响评分。最终complete\_us必须与评测器复算结果一致。

## F.3 输出合法性

每个未命中iocb的有效范围必须恰好覆盖一次。不允许遗漏、重复、越界、引用不存在的iocb或为同一数据同时选择多个前台路径。

DIRECT必须满足三项512B对齐。AGGREGATE和FALLBACK可以扩展物理SSD范围，但扩展数据不能写入无关目标HBM。跨iocb AGGREGATE只能合并同卡且SSD地址连续或相邻的范围。

PROMOTE必须引用已经完整完成的iocb，并覆盖该iocb的完整有效数据。PROMOTE\_SSD使用完整SSD有效范围，PROMOTE\_HBM使用完整目标HBM有效范围。

# 附录G：约束、目标函数

## G.1资源约束

任意时刻必须满足：

NdsForegroundIocbInflight(t) ≤ iocb\_capacity  
  
AggregateUsed(t) ≤ hbm\_capacity  
  
FallbackUsed(t) ≤ ddr\_capacity  
  
KVCachePoolUsed(t) ≤ kvcache\_pool\_capacity

## G.2 CPU和NPU成本

CPUCost(o) = CPUBase(path(o))  
  
           + CPUCmd(path(o)) × Commands(o)  
  
           + CPU\_H2D\_CALL\_COST × H2DCalls(o)  
  
           + CPU\_D2H\_CALL\_COST × D2HCalls(o)  
  
           + CPU\_D2D\_CALL\_COST × D2DCalls(o)  
  
NPUCost(o) = NPU\_H2D\_CALL\_COST × H2DCalls(o)  
  
           + NPU\_D2H\_CALL\_COST × D2HCalls(o)  
  
           + NPU\_D2D\_CALL\_COST × D2DCalls(o)

CPU/NPU COST不是执行时间。传输时间只通过性能桶计入TraceTime。

## G.3优化目标

TraceTime = 最终前台及已启动PROMOTE完成时间 - 第一个submit到达时间  
  
EffectiveBandwidth = ValidBytes / TraceTime  
  
J = time\_cost\_per\_us × TraceTime + ΣCPUCost + ΣNPUCost

ValidBytes只统计逻辑有效数据，不包括对齐扩展产生的额外物理字节。
