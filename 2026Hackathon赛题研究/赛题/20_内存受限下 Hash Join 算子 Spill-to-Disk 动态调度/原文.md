# 内存受限下 Hash Join 算子 Spill-to-Disk 动态调度

来自技术领域：数据库 - 执行器  

一、背景信息（赛题产生的业务背景）

在现代数据库执行引擎（如 DuckDB、Velox、Greenplum、OceanBase）中，Hash Join 和 Hash Aggregation 是最核心也是最消耗内存的算子。在处理大规模数据时，Hash 表的构建往往需要占用数 GB 甚至数十 GB 内存。当系统可用内存不足以容纳全部 Hash 数据时，执行引擎必须采用 Spill-to-Disk（落盘）策略：将部分 Hash 分区（Partition）从内存写出到磁盘，待后续 Probe 阶段需要时再从磁盘加载回来。

这一过程存在多重核心矛盾：

- **内存约束与数据规模的矛盾**：系统总内存有限，而实际数据量可能远超内存容量，必须进行选择性落盘。
- **落盘时机与 I/O 开销的矛盾**：过早落盘可能导致后续 Probe 阶段频繁触发磁盘读取，产生大量 I/O 开销；过晚落盘则可能导致内存溢出（OOM），系统直接崩溃。
- **分区选择与 I/O 抖动的矛盾**：如果落盘的是即将被 Probe 访问的"热点"分区，会造成"刚写出又读回"的 I/O 抖动，严重浪费磁盘带宽。
- **多算子并发的资源竞争**：当多个 SQL 查询并发执行时，不同算子之间争夺有限的内存资源，需要动态调配内存配额。

业界主流数据库均实现了 Spill-to-Disk 机制，但采用的策略各异：PostgreSQL 采用简单的批量落盘与逐分区重载，DuckDB 基于 Partition-level 粒度的自适应落盘与预取，Greenplum 则采用了多级 Grace Hash Join 策略。在数据倾斜、并发查询和有限内存的综合压力下，如何设计高效的 Spill 调度策略仍是数据库领域持续优化的方向。

本赛题要求选手在给定内存约束下，设计并实现 Hash Join 算子的 Spill-to-Disk 调度策略。系统模拟多个并发 Hash Join 算子的 Build 与 Probe 全流程，选手需实现调度器，决定何时落盘、落盘哪些分区、何时加载、如何在多算子间分配内存，在保证不发生 OOM 的前提下，最小化总执行延迟与磁盘 I/O 开销。

## 二、问题描述（现状、技术挑战等）

### 2.1 系统模型

系统包含以下核心参数：

- **总内存 M**：系统可用于所有 Hash 分区的内存上限（单位：字节）。
- **磁盘带宽**：
- 顺序写带宽 W（单位：字节/微秒）：向磁盘写入数据的速率。
- 顺序读带宽 R（单位：字节/微秒）：从磁盘读取数据的速率。
- **算子数量 K**：系统中并发执行的 Hash Join 算子数量。
- **分区数 P**：每个算子的 Hash 表被划分为 P 个分区（Partition 0 ~ P-1）。
- **Hash 函数**：partition\_id = key % P。
- **Miss 惩罚值**：每次 Probe 未命中的额外惩罚（单位：微秒）。

### 2.2 数据结构

|  |
| --- |
| 分区（Partition）属性：  - partition\_id：分区编号，取值范围 [0, P-1]  - data\_size：当前分区中数据的总大小（字节）  - in\_memory：当前是否在内存中（true/false）     算子（Operator）属性：  - op\_id：算子编号，取值范围 [0, K-1]  - phase：当前阶段，取值为 BUILD（构建阶段）或 PROBE（探测阶段）  - partitions：P 个分区的状态列表     系统状态：  - memory\_used：当前所有 in\_memory 分区的 data\_size 之和  - memory\_limit：等于 M |

### 

### 2.3 操作定义

工作负载文件包含三类操作，按序执行：

**（1）INSERT op\_id key size**

向指定算子的 Hash 表插入一个元组。

执行逻辑：

1. 计算 partition\_id = key % P。
2. 若该分区 in\_memory = true：

- 若 memory\_used + size ≤ M，直接插入，memory\_used += size，分区 data\_size += size。
- 若 memory\_used + size > M，**内存溢出**——调度器必须先选择若干 in\_memory 分区落盘，释放足够空间后再插入。

1. 若该分区 in\_memory = false（已在磁盘上）：

- 该元组直接写入磁盘，I/O 耗时 = size / W，分区 data\_size += size，memory\_used 不变。

**（2）SWITCH op\_id**

将指定算子从 BUILD 阶段切换到 PROBE 阶段。无时间开销，不计入周期性调度的操作计数。

**（3）PROBE op\_id key**

在指定算子中探测一个键。

执行逻辑：

1. 计算 partition\_id = key % P。
2. 若该分区 in\_memory = true → **命中（Hit）**，耗时可忽略，不计入评分。
3. 若该分区 in\_memory = false → **未命中（Miss）**：

- 必须将该分区从磁盘加载到内存后才能执行探测。
- 若 memory\_used + partition.data\_size ≤ M，直接加载。
- 若 memory\_used + partition.data\_size > M，调度器必须先选择若干 in\_memory 分区落盘，释放足够空间后再加载。
- 加载耗时 = partition.data\_size / R，加载后 in\_memory = true，memory\_used += partition.data\_size。
- 累计 miss\_count += 1。

### 

### 

### 2.4 落盘与加载操作

**落盘（SPILL）**：将一个 in\_memory 分区的数据写出到磁盘。

- 耗时 = partition.data\_size / W。
- 落盘后：in\_memory = false，memory\_used -= partition.data\_size。
- 分区的 data\_size 不变（数据仍存在磁盘上）。

**加载（LOAD）**：将一个 on-disk 分区的数据从磁盘读入内存。

- 前提：memory\_used + partition.data\_size ≤ M（否则需先落盘其他分区）。
- 耗时 = partition.data\_size / R。
- 加载后：in\_memory = true，memory\_used += partition.data\_size。

**约束**：

- 任意时刻，memory\_used ≤ M，否则判定为 OOM，该测试用例得 0 分。
- 分区具有原子性：一个分区的数据要么全部在内存中，要么全部在磁盘上。
- 一个算子处于 BUILD 阶段时，其分区只能被落盘；处于 PROBE 阶段时，其分区可以被落盘或加载。

### 2.6 样例说明

**参数**：K=1, P=3, M=256 字节, W=100 字节/μs, R=80 字节/μs, miss\_penalty=10μs

**Build** **阶段**（6 个元组，每个 64 字节）：

|  |  |  |  |  |  |
| --- | --- | --- | --- | --- | --- |
| **步骤** | **操作** | **分区** | **内存中各分区大小** | **memory\_used** | **说明** |
| 1 | INSERT key=0 | p0=64 | {p0:64, p1:0, p2:0} | 64 |  |
| 2 | INSERT key=3 | p0=128 | {p0:128, p1:0, p2:0} | 128 | key=3→3%3=0 |
| 3 | INSERT key=1 | p1=64 | {p0:128, p1:64, p2:0} | 192 |  |
| 4 | INSERT key=4 | p1=128 | {p0:128, p1:128, p2:0} | 256 | memory\_used=M，满 |
| 5 | INSERT key=2 | p2=? | 需64字节 | 256+64>M | \*\*内存溢出！调度器介入\*\* |

 

**调度器决策**（步骤5）：

- 需释放至少 64 字节。
- 当前 in\_memory 分区：p0(128), p1(128), p2(0)。
- 朴素策略：选择最大分区 p0 落盘。落盘耗时 = 128/100 = 1.28μs。
- 落盘后：p0 → on\_disk，memory\_used = 128。
- 插入 key=2：p2=64，memory\_used = 192。

|  |  |  |  |  |  |
| --- | --- | --- | --- | --- | --- |
| **步骤** | **操作** | **分区** | **内存中各分区大小** | **memory\_used** | **I/O耗时** |
| 5' | SPILL p0 | p0→disk | {p1:128, p2:0} | 128 | 1.28μs |
| 5'' | INSERT key=2 | p2=64 | {p1:128, p2:64} | 192 | - |
| 6 | INSERT key=5 | p2=128 | {p1:128, p2:128} | 256 | key=5→5%3=2 |

 

SWITCH op0 → 进入 PROBE 阶段。

**Probe** **阶段**（4 个探测键）：

|  |  |  |  |  |  |  |
| --- | --- | --- | --- | --- | --- | --- |
| **步骤** | **操作** | **目标分区** | **状态** | **结果** | **I/O动作** | **I/O耗时** |
| 7 | PROBE key=0 | p0 | on\_disk | \*\*Miss\*\* | SPILL p2(128)+LOAD p0(128) | 128/100+128/80=2.88μs |
| 8 | PROBE key=1 | p1 | in\_memory | \*\*Hit\*\* | - | - |
| 9 | PROBE key=2 | p2 | on\_disk | \*\*Miss\*\* | SPILL p0(128)+LOAD p2(128) | 2.88μs |
| 10 | PROBE key=3 | p0 | on\_disk | \*\*Miss\*\* | SPILL p2(128)+LOAD p0(128) | 2.88μs |

 

**统计**：

- Hit = 1，Miss = 3
- 总 I/O 耗时 = 1.28(build spill) + 2.88×3(probe) = 9.92μs
- 总惩罚 = I/O耗时 + miss\_penalty × miss\_count = 9.92 + 10×3 = 39.92μs

**对比**：若步骤5中调度器选择落盘 p1 而非 p0，则 Probe 阶段 p0(128) 留在内存中。此时 PROBE key=0 和 PROBE key=3 均可命中（p0 in\_memory），仅 PROBE key=2 需加载 p2，Hit=2、Miss=1，总惩罚显著降低。这体现了**落盘分区选择策略对最终性能的关键影响**。

## 三、期望达到的指标和效果（含性能/精度等指标）

**功能目标**：

- 在给定内存约束下正确执行全部工作负载，不出现 OOM。
- 正确统计命中/未命中次数和磁盘 I/O 开销。
- 所有分区状态转换逻辑正确，memory\_used 在任意时刻不超过 M。

**性能目标**：

- 数据规模：K ≤ 8 个并发算子，P ≤ 64 个分区，总操作数 ≤ 5,000,000。
- 内存上限 M：64MB ~ 4GB。
- 评估公式：Score = Total\_IO\_Time + miss\_penalty × miss\_count，越小越优。
- Total\_IO\_Time：所有落盘和加载操作的 I/O 耗时之和（微秒）。
- miss\_count：所有 PROBE 操作中分区未命中的总次数。
- miss\_penalty：每次未命中的惩罚值（由测试数据给出）。
- 硬件环境：8 核 CPU、8GB 内存、256GB SSD。

## 四、测试用例

### 输入格式

第一行包含 6 个参数：

|  |
| --- |
| K P M W R miss\_penalty |

- K：算子数量（1 ≤ K ≤ 8）
- P：每算子分区数（2 ≤ P ≤ 64）
- M：内存上限（字节，64MB ≤ M ≤ 4GB）
- W：磁盘顺序写带宽（字节/微秒，1 ≤ W ≤ 10000）
- R：磁盘顺序读带宽（字节/μs，1 ≤ R ≤ 10000）
- miss\_penalty：每次 Probe 未命中的惩罚值（微秒，1 ≤ miss\_penalty ≤ 1000）

第二行包含两个整数：

|  |
| --- |
| N B |

- N：操作序列总条数（1 ≤ N ≤ 5000000）
- B：周期性调度的间隔（每 B 个操作触发一次 onPeriodicAdjust，1 ≤ B ≤ 10000）

接下来 K 行，每行 3 个整数：

|  |
| --- |
| op\_id build\_count probe\_count |

- op\_id：算子编号（0 ≤ op\_id < K）
- build\_count：该算子的 Build 元组数
- probe\_count：该算子的 Probe 元组数

接下来 N 行，每行描述一个操作：

|  |
| --- |
| INSERT op\_id key size  SWITCH op\_id  PROBE op\_id key |

- INSERT：插入元组，0 ≤ key ≤ 10^9，1 ≤ size ≤ 1048576
- SWITCH：切换算子阶段
- PROBE：探测键

**输入约束**：

- 每个 operator 的 INSERT 操作必须在其 SWITCH 之前。
- 每个 operator 的 PROBE 操作必须在其 SWITCH 之后。
- 每条 key 对应的 partition\_id = key % P，输入保证数据倾斜存在（部分分区远大于其他分区）。

### 输出格式

程序输出到标准输出，格式如下：

|  |
| --- |
| Total\_IO\_Time: <value>  Hit\_Count: <value>  Miss\_Count: <value>  Total\_Score: <value> |

- Total\_IO\_Time：所有落盘与加载操作的 I/O 耗时之和（微秒，保留 2 位小数）。
- Hit\_Count：Probe 命中总次数。
- Miss\_Count：Probe 未命中总次数。
- Total\_Score = Total\_IO\_Time + miss\_penalty × Miss\_Count。

- 框架代码已实现完整的执行引擎和朴素调度策略（NaiveSpillScheduler）。
- 朴素策略的行为：内存溢出时落盘最大分区；Probe 未命中时落盘最大分区腾空间后加载目标分区；不做主动调整。
- 参赛者需替换 NaiveSpillScheduler 为自己的实现，优化落盘/加载决策。
- 引擎在执行调度器返回的动作后，会校验内存约束和分区状态。若 INSERT 后仍超出内存上限、LOAD 后超出内存上限、或 PROBE 后目标分区仍不在内存中，引擎将输出 OOM 错误并退出（比赛评测时判定为 OOM，该用例得 0 分）。
- SWITCH 操作不计入周期性调度的操作计数（即只有 INSERT 和 PROBE 计入 B 的计数）。
