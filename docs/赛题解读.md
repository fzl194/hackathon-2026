# 第14题解读：把向量搜索真正做进PostgreSQL

整理日期：2026-10-21。官方要求以[本次重新获取的题面](赛题原文.md)为准；以下方案是研究判断，尚未实现或跑分。

## 用图书馆理解任务

每篇文档有一张数字指纹卡，查相似内容就是找指纹最接近的几张。图书馆太大后，导航目录放不进内存，需要大部分存硬盘；同时还得支持新增、修改、删除、按标签找书，以及事务撤销和故障恢复。

所以本题的成品是数据库索引扩展。独立ANN库能找近邻，只解决一部分问题；还必须让PostgreSQL正确管理索引、可见性和持久化。

## 交付与硬要求

- 基于PostgreSQL 18.4的扩展源码；优先按不修改内核的路线准备。
- 符合big-ann-benchmarks规范的Dockerfile、参数扫描config.yml及不超过8页报告。
- 类型为vector、halfvec、sparsevec、bit。前三类要求L1/L2/负内积/余弦；bit要求汉明/Jaccard。
- 支持3072维数据建索引；8000维float32是期望目标，不能与3072维淘汰门槛混为一谈。
- 完整事务、插入更新删除、并发读写、标签过滤与规划器集成。
- 索引规模超过内存时仍能工作，不能只展示全驻内存的小例。

超RAM、缺必需距离或无法在指定3072维数据上建索引会淘汰。具体测试矩阵和仍不明确的口径见[实施与验证](实施与验证.md)、[待确认事项](待确认事项.md)。

## 技术路线先看功能差距

pgvector可用作类型、距离、精确查询及成熟数据库行为的参照。其文档列HNSW的vector索引上限2000维、halfvec为4000维，类型存储上限与特定索引上限不同；不要把“能存3072维”当作“已完成所需高维索引”。[官方说明](https://github.com/pgvector/pgvector)

pgvectorscale已有StreamingDiskANN、量化和标签过滤，是磁盘搜索候选基线。其README列L2、余弦和内积；标签采用smallint[]及OR overlap，带标签索引不支持并行构建。这些与本题完整距离、约20万标签及AND过滤有差距，需要功能与性能验证，不能直接视为合规成品。[官方说明](https://github.com/timescale/pgvectorscale)

可研究导航向量压缩、精确重评分、页布局、缓存和过滤策略。选择开源基线后先锁定具体版本/提交与许可，再补功能；不要先追一个QPS数字而留下硬要求缺口。

## 数据、硬件与AI的作用

本题采用公开基准，能提前准备小规模数据与真值，再扩大到超内存测试。公开基准不等于已经取得比赛调度脚本、正式VM或完全相同的数据版本。

无需训练基础大模型。聚类/量化训练属于可选实现，CPU、SSD及构建周转更关键。以1B×128维float32计，纯向量载荷约512GB；这是存储方式推算，不含索引、WAL和临时文件，也不代表所有数据包均为float32。

AI适合帮助读代码、生成回归与反例、实现局部模块、分析性能和参数实验。事务、恢复与真实性能必须运行验证；不能因为AI能生成代码，就假定已满足ACID或获得官方收益。
